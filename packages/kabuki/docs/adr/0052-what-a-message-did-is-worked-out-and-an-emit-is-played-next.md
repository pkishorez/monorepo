# What a Message did is worked out, and an Emit is played next

**Status:** proposed

Amends [ADR 0044](0044-a-child-emits-to-its-parent-and-is-made-with-child.md) and [ADR 0051](0051-an-instance-tries-a-message-without-sending-it.md). A tool that explains an app, a person in the DevTools or an agent through MCP, asks three things of every Message: what it did across the tree, what it set off at once, and whether the work it asked for is going well. Kabuki answers the first only as two Snapshots to compare by hand, the second only by luck of order, and the third only as a Worker's status with no reason. So it gains three things, each in the folder it belongs to, and the History still keeps only a start Snapshot and Messages.

**A Change is what a Message did, worked out from the Snapshots around it.** `Snapshot.changes(actor, before, after)` compares any two Snapshots, skipping every part that is the same object in both, so comparing one Message's Snapshots walks only the path it changed. It says, per Address: an Instance added, with its whole data, or removed, with its data before; its State before and after; each Model field before and after, compared by `Object.is` as an Update's fields are merged; each Props field before and after, compared by `Equal.equals` as a Child is handed them; and the Workers its data now asks for or no longer does, from `Snapshot.workers` before and after, `each` keys included. A Change is read from a Message and the Snapshot before it alone, so it is never kept. `Snapshot.next` does not give one: it runs for every live Message, and the Runtime, which needs none, would pay for it. `instance.try` gives one beside what it gives now.

**A Chain is one Message and the Emits it set off, played together.** Handling a Message is synchronous ([ADR 0010](0010-handling-a-message-is-synchronous.md)), and the only Messages an Update makes at once are its Emits. A Command's answer, a Worker's Send, a View's and one from outside all come later, each from its own Source. So the Mailbox plays what an Update Emitted before anything already waiting: the parent's Message comes right after the Child's, as ADR 0044 meant, and the grandparent's right after that, depth first. Each is stamped with the Time of the entry that Emitted it: a Chain happens at one Time, so Times still only grow along the History. A Chain is an entry whose Source is not an Emit, and every Emit entry right after it. It is read from the History's order alone, so nothing new is kept. Who Sent the first entry is its Source, which already names the Instance and the part of it that Sent: its View, a Worker by name and key, a Command by name, what it Provides, or outside by name. A Capability's function Sends with the Source of the Worker or Command that called it, since the Runtime keeps who is running in the fiber's context, `Sending`, and the Capability's function runs in the caller's fiber.

**The Work report is what the running app is doing, read from the Runtime alone.** `runtime.work()` says, for every Instance now: each Worker as `waiting` for the Capabilities above it, `running`, `finished` or `failed`, with the failure and the Time it started; each Command still running, with its name, its args and the Time it started; and each Provide, at its top and in its State, as `building`, `built` or `failed`, with the failure; and the app's Layer the same way. Beside it is a short list of the latest failures of Workers, Commands, Provides and the Layer, each with its Address, so one is not lost when its Instance stops. Failures still reach the console. None of it is in a Snapshot or a History ([ADR 0048](0048-the-runtime-is-a-snapshot-kept-alive.md)): a past Step has no Work report.

## Considered Options

- **`Snapshot.next` giving the Change in `Played`**: rejected. Every live Message, every Replay and every tool's replay would compute it, and only a tool reads it. A Change beside the Runtime's own work also invites driving the live tree from it, which ADR 0048 rejected as a flat diff of plans.
- **Keeping each Message's Change in the History**: rejected, as [ADR 0023](0023-a-log-entry-is-what-replay-needs-and-who-sent-it.md) rejected it. It is the same truth twice, and a History replayed against changed code would show what the old code did.
- **Keeping a Cause on every entry**, the entry that led to it: rejected. For an Emit the order now says it. For a Command's answer it would link work that happened later, which is not what a Chain is, and it means numbering entries in the Runtime, mapping them in every History, and saving them.
- **Working a Chain out as now, from whatever order the Mailbox gave**: rejected. A Message queued while the Child's was played, a Worker's say, lands between the Child's entry and its parent's, and the Chain breaks.
- **Naming the Capability a Message came through**: left out. A Capability is a value in a Layer; naming it means wrapping every Service.
- **Worker status in the Snapshot**: rejected again. It is what the running work does, not data; Replay could never give it.

## Consequences

- What an Update Emits is played before Messages that were already waiting. An app whose order relied on the old queue sees its parent hear the Child sooner.
- A Chain whose first entry was Compacted out of the Window starts at the oldest entry kept, and a tool shows it as cut.
- A Command's answer names its Command and its Instance, not which entry asked for it. Linking the two is left out.
- A Capability's Service that runs a fiber of its own, made when its Layer is built, Sends with no caller and is named `provides`. A Query that calls a Capability is named `provides` too.
- Restarting the work, as a Fork or `start` does, starts every Worker again with no entry; the Work report shows them, a Change never does.
- A tool can wait for **Settled**: no Command running, every Provide built, and no entry for a moment. An empty Mailbox is not enough, since it drains before a Send returns and a Worker Sends whenever it likes.
