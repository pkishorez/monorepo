The Playlist from the last page has a new job: playing music. It decides
which song plays. But each Song should show it, with a little animation
next to its title.

In React, you'd pass it down as a prop: `<Song playing={id === playing} />`.
kabuki does exactly the same. A parent hands each Child its **Props**.

## Props flow down

Props are what the parent says now. Every time the parent's Model or State
changes, kabuki works its Props out again and hands them down.

<Demo caption="A Message changes the Playlist. Then its Props flow down, and each Song sees whether it is the one playing. The Songs only read them.">
  <PropsPicture />
</Demo>

You write them beside the Child, as a function of the parent's data:

```ts
songs: {
  actor: SongLive,
  each: ({ model }) => model.ids,
  input: (_, id) => SONGS[id],
  props: ({ model }, id) => ({ playing: model.playing === id }),
},
```

The Child says what Props it takes in its Definition, so the parent can't
hand it the wrong shape:

```ts
props: Schema.Struct({ playing: Schema.Boolean }),
```

## A Child reads them, and never writes them

The Song's View gets its Props, the same as in React. So do its Updates,
with every Message, and its Workers' tests. Wherever the Song makes a
decision, it can see what its parent says.

But it can never change them. Only the parent can. That keeps the story
simple: data flows down, one way.

## Input or Props?

The Song now gets two things from its parent, and they're different.

- **Input** is read once, when the Child starts. The title is Input: the
  Song keeps it as its own.
- **Props** are read live, and change whenever the parent's data does.
  `playing` is a Prop: the Playlist decides it, all the time.

If the Child should own it, use Input. If the parent should keep deciding
it, use Props.
