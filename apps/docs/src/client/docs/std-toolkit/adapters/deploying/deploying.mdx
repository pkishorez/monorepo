SQLite and DynamoDB need their table to exist before a request can use
it. Someone has to make it, and has to make sure a new release doesn't
break the rows already in it. This page shows how std-toolkit does both as
part of your deploy, with Alchemy.

## A table is infrastructure

Your server's database is made when you deploy, the same as your Worker and
your domain. `@kestack/std-toolkit/deploy` gives you Alchemy resources for
your tables:

- `D1.table` sets up a table in a Cloudflare D1 database.
- `DynamoDB.table` creates a DynamoDB table and sets it up.
- `D1.migration` and `DynamoDB.migration` move every row of an old table
  into a new one, once.
- `DeployGuard.table` guards a table your deploy doesn't set up, such as
  one in IndexedDB or a Durable Object.
- `providers()` gives your stack what these resources need.

Each table resource takes a required `mode`, the same **Table mode** the
adapters take.

## Setup runs at deploy

A D1 or DynamoDB table resource runs the table's setup during the deploy,
before your Worker goes live. Setup compares your table with the
**Stored contract** kept inside it. If the new table would break rows
already stored, the deploy fails, before the table is touched. If an
index changed, setup reindexes the rows it touches, and the deploy waits
for it.

There's no override. The way past a breaking change is to undo it and add a
new version, or to move the data to a new table with a [table
migration](/std-toolkit/table-mode).

## A D1 table

Here a Worker's D1 table is set up at deploy. `D1.table` runs
`SQLite.setup` for you, so the Worker never does.

```ts
import * as Cloudflare from '@alchemy.run/cloudflare';
import { Stack, Stage } from 'alchemy';
import * as Effect from 'effect/Effect';
import * as Layer from 'effect/Layer';
import { D1, providers } from '@kestack/std-toolkit/deploy';
import { boardTable } from './src/table.ts';

export const Database = Cloudflare.D1.Database(
  'Database',
  Effect.gen(function* () {
    return { name: `board-${yield* Stage}` };
  }),
);

export const Worker = Cloudflare.Website.Vite(
  'Worker',
  Effect.gen(function* () {
    const database = yield* Database;
    const table = yield* D1.table('BoardTable', {
      table: boardTable,
      database,
      mode: 'persistent',
    });
    // Binding the table's name makes the Worker wait for its setup.
    return { env: { DB: Database, DB_TABLE: table.tableName } };
  }),
);

export default Stack(
  'Board',
  {
    providers: providers().pipe(Layer.provideMerge(Cloudflare.providers())),
    state: Cloudflare.state(),
  },
  Worker,
);
```

The Worker binds `table.tableName`, so Alchemy deploys it only after setup
and its reindex. A Worker that binds only the database may go live
first. At runtime, the Worker builds its layer from that name,
`SQLite.make(boardTable, { database, tableName: env.DB_TABLE })`, and runs
no setup.

## The other two

`DynamoDB.table` takes the table, a `tableName`, a mode and a `region`.
It creates a missing table and runs setup at deploy, against the Stored
contract inside it, just as D1 does. It never replaces a table: it adds a
new global secondary index in place, but any other index change fails,
and so does renaming the table under the same resource.

`DeployGuard.table(table)` is for a persistent table whose setup runs
later, on a device or an object, like one in your users' browsers. Your
deploy can't reach that data, so the guard keeps the contract you last
shipped in Alchemy's state, and fails the deploy on a change setup would
refuse. Declaring it makes the table persistent, and one guard covers
every place that table lives. D1 and DynamoDB tables need none.

## More than one check

Setup at deploy isn't the only check. Wherever a table opens, on SQLite,
IndexedDB or a Durable Object, setup compares it with the Stored contract
inside it. And the [Snapshot](/std-toolkit/snapshot) test catches a
breaking change before you even deploy. Each catches what the one before
might miss.

<Callout title="Remember">
  Declare each server table with its mode. Its setup runs on every deploy, and a
  change that would break a persistent table's rows never reaches them.
</Callout>
