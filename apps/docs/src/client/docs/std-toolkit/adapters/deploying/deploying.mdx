SQLite and DynamoDB need their table to exist before a request can use
it. Someone has to make it, and has to make sure a new release doesn't
break the rows already in it. This page shows how std-toolkit does both as
part of your deploy, with Alchemy.

## A table is infrastructure

Your server's database is made when you deploy, the same as your Worker and
your domain. `@kestack/std-toolkit/alchemy` gives you Alchemy resources for
your tables:

- `D1.table` sets up a table in a Cloudflare D1 database.
- `DynamoDB.table` creates a DynamoDB table and every index.
- `providers()` gives your stack what these resources need.

Each table resource takes a required `mode`, the same **Table mode** the
adapters take.

## The check at deploy

Every table keeps a snapshot of the shape it was last set up under, as a
few rows of its own. Every deploy, `D1.table` and `DynamoDB.table` compare
your table with that snapshot. If the new table would break rows already
stored, the deploy fails, before the table is touched. Then the new
snapshot is written.

The snapshot lives with the data, not in Alchemy's state. Lose the state,
and the next deploy is still checked against the rows it would break.

There's no override. The way past a breaking change is to undo it and add a
new version, or to move the data to a table with a new name.

## A D1 table

Here a Worker's D1 table is set up at deploy. On D1, `D1.table` also runs
`SQLite.setup` for you, so the Worker never does.

```ts
import * as Cloudflare from '@alchemy.run/cloudflare';
import { Stack, Stage } from 'alchemy';
import * as Effect from 'effect/Effect';
import * as Layer from 'effect/Layer';
import { D1, providers } from '@kestack/std-toolkit/alchemy';
import { boardTable } from './src/table.ts';

export const Database = Cloudflare.D1.Database(
  'Database',
  Effect.gen(function* () {
    return { name: `board-${yield* Stage}` };
  }),
);

export const Worker = Cloudflare.Website.Vite(
  'Worker',
  Effect.gen(function* () {
    const database = yield* Database;
    yield* D1.table('BoardTable', {
      table: boardTable,
      database,
      mode: 'persistent',
    });
    return { env: { DB: Database } };
  }),
);

export default Stack(
  'Board',
  {
    providers: providers().pipe(Layer.provideMerge(Cloudflare.providers())),
    state: Cloudflare.state(),
  },
  Worker,
);
```

Entities add themselves to a table as their modules load. So import every
module that binds an entity before the table resource runs, or the check
won't see them.

## A DynamoDB table

`DynamoDB.table` takes the table, a `tableName` and a mode. Before Alchemy
changes the table, it reads the snapshot from the live table and checks
your table against it. Once the table is changed, it writes the new one.

It reaches the table with the AWS account and region your stack deploys
with, so give your stack AWS's providers under std-toolkit's. Without
them, the deploy fails and says so:

```ts
import * as AWS from '@alchemy.run/aws';
import { Stack } from 'alchemy';
import * as Effect from 'effect/Effect';
import * as Layer from 'effect/Layer';
import { DynamoDB, providers } from '@kestack/std-toolkit/alchemy';
import { boardTable } from './src/table.ts';

export default Stack(
  'Board',
  {
    providers: providers().pipe(Layer.provideMerge(AWS.providers())),
    state: AWS.state(),
  },
  Effect.gen(function* () {
    yield* DynamoDB.table('BoardTable', {
      table: boardTable,
      tableName: 'board',
      mode: 'persistent',
    });
  }),
);
```

To read the physical table's keys and indexes outside a deploy, or tell
whether it's there yet, use `DynamoDB.describeTable(config)` from
`@kestack/std-toolkit/db/dynamodb`.

It never replaces or wipes a DynamoDB table, in either mode. A change only a
new table could make fails, and so does renaming the table under the same
resource. The way past is a new `DynamoDB.table`, with its own id and table
name.

Under `alchemy dev`, it doesn't work yet: Alchemy keeps the table on real
AWS, while the check reads and writes the local emulator. Deploy a
DynamoDB table to a stage instead.

## More than one check

A table your deploy doesn't create, like one in a Durable Object or in your
users' browsers, runs the same check itself, each time it's set up. And the
[Snapshot](/std-toolkit/snapshot) test catches a breaking change before you
even deploy, for every table. Each catches what the one before might miss.

<Callout title="Remember">
  Declare each server table with its mode. A persistent table is checked on
  every deploy, and a change that would break its rows never reaches them.
</Callout>
