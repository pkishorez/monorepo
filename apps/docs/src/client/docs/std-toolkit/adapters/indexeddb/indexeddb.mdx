A Memory table is gone when the page reloads. That's fine for a demo, but
a web app should open with its data, even offline. The browser has a
database of its own for that, IndexedDB, and this page puts your table in
it.

## The same table, kept

The IndexedDB adapter takes the same table and gives it a home in the
browser. Each table becomes one **Store** in an IndexedDB database. Its
rows outlive a reload, a closed tab, a restart.

These docs keep nothing in your browser, so this page shows the code and a
picture rather than a live table. The program is the one you ran on
[Memory](/std-toolkit/memory).

`IDB.database` opens a database by name, once, and every table that uses it
shares the connection. `IDB.make` gives the table its Store, named after
the table unless you pass `storeName`.

## Mode is required

Memory needs no mode because nothing outlives it. IndexedDB keeps rows, so
you must say what a change to the table's shape may cost them. That is the
**Table mode** you met in [Table mode](/std-toolkit/table-mode):

- `persistent`: these rows must never be lost. A change that would break
  them is refused, and the Store is never wiped.
- `disposable`: these rows can be fetched again. A change they can't take,
  a new index included, throws them away and starts over.

A local copy of server data, like the tasks above, is disposable. Data that
lives only in this browser, like a draft nobody else has, is persistent.

## Setup happens on open

The first time a table opens its database, the adapter prepares the Store.
It compares the table with the **Stored contract**, kept as reserved rows
inside the Store, and decides what the change means under the mode. Then
it makes the indexes match in a version change, reindexes the rows an
index change touches, and records the new contract.

IndexedDB makes a version change wait for other open tabs. If you'd rather
choose that moment, call `IDB.setup(table, config)` yourself, and handle a
persistent Store's `SetupRefused` there.

The adapter owns the database's version number. Give it a database name no
other code opens with its own version.

## Many tabs, one Store

Every tab of your app opens the same Store. Two tabs can edit one task at
once, so a read-then-write checks that `_u`, the task's update key, hasn't
moved since it read. If another tab got there first, the write fails, and
you can try again.

## Cleaning up

Databases you no longer use stay in the browser.
`IDB.prune({ prefix, keep })` deletes every database under a prefix except
the ones you name. You
say what you keep, never what you drop, so a database you forgot about
still goes.

  IndexedDB keeps your table across reloads, and it asks for a mode:
  `disposable` for a copy you can fetch again, `persistent` for data that lives

</Callout>
