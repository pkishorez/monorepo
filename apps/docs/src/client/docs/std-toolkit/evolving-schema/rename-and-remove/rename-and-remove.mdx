So far every new version has added a field: a priority, then `done`. Adding
is the easy change, because nothing old is lost. This page covers the
others: taking a field away, giving one a new name, and changing what a
field holds. Each is still one `evolve` step.

## The delta names what changed

The second argument of `evolve` is the **delta**: only the fields that
changed. A field you don't mention carries over as it was. A delta can do
three things:

- **Add** a field: name it with its Schema.
- **Remove** a field: name it with `null`.
- **Change** a field: name an existing one with a new Schema.

There's no fourth move for a rename. A rename is a remove and an add in
the same step, and the migration moves the value from one to the other.

Release 4 renames `title` to `name`. The delta removes `title` and adds

## Nothing is lost until a save

A read never writes. So a task saved at v3 still holds `title` and `done`
in the table, after release 5 has read it many times. Release 5 just never
sees them. They're gone from storage only when that task is saved again,
in the v5 shape.

Keep that in mind before you remove a field you might want back. Until a
row is saved again, its old value is still there. After, it isn't.

## Changing what a field holds

To change a field's type, name it again with its new Schema. Say an early
release kept an estimate as text, and now it should be a number:

```ts
.evolve('v2', { estimate: Schema.Finite }, (v1) => ({
  ...v1,
  estimate: Number(v1.estimate),
}))
```

This one needs care. The migration must work for **every** text v1 could
have held, not only the ones you have in mind. What is `Number('a
while')`? It's `NaN`, which v2 refuses, so that task would fail to read.
The [Upgrade check](/std-toolkit/upgrade-check) finds rows like that before
you ship.

<Callout title="Remember">
  `null` in a delta removes a field. A rename is a remove plus an add, and the
  migration carries the value across. Old values stay in storage until a row is
  saved again.
</Callout>
