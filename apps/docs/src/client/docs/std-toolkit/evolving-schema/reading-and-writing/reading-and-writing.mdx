You've added a version, and old tasks read in the new shape. This page
slows that down: what a read does step by step, what a write does, and why
the two are not mirror images.

## A read, step by step

Say a task has three versions: v2 added `priority`, v3 added `done`. A row
saved at v1 is read. Four things happen, in order:

1. **Read the stamp.** The row's `_v` says which version wrote it. A row
   with no `_v` at all is read as v1.
2. **Decode at that version.** The row is checked against v1's fields, not
   the latest's. A v1 row is a perfectly good v1 task.
3. **Run each migration after it**, one at a time: v1 → v2 adds a priority,
   then v2 → v3 adds done.
4. **Hand over the latest value.** Your code gets a v3 task, and never sees
   which version it came from.

## A write always uses the latest

Writing has no steps to speak of. Your code holds a latest value, so
encoding it stamps the latest version, `_v: 'v3'`. No migration ever runs on
a write.

So reading looks back, through every version, and writing looks forward,
to the latest only. Keeping all the history on the read side is what lets
the write side stay this simple.

Encoding and decoding convert each such field for you, so your code never
handles the string. Migrations work on values too, so a migration can build
a `Date` from an old string field.

## When a read cannot work

One row can't be read: one stamped with a version newer than your code
knows. That happens when an older release meets data a newer one saved.
[Gotchas](/std-toolkit/gotchas) covers it, and what to do.

<Callout title="Remember">
  A read decodes at the row's own version and migrates forward to the latest. A
  write always stamps the latest. Migrations never run on a write.
</Callout>
