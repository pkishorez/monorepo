So far your task has been an **ESchema**: a name, its fields, and every
version it has had. That's enough to describe one task. But an app keeps
many tasks, and to save them you need to tell one from another. This page
adds the one thing missing: an id.

## One more argument

An **EntityESchema** is an ESchema that also carries an id. That's the
whole difference. You write it the same way, with one more argument: the
name of the id field.


And here it is as an EntityESchema:

Same name, same fields, same `evolve` step. The new argument, `'taskId'`,
is the **id field**. Notice you don't list it with the other fields.

## The id is the builder's

You don't list `taskId` because the builder adds it for you, as a string,
to **every** version: v1, v2 and every version after. No `evolve` step may
add it, remove it or change it. Try, and it doesn't compile.

<Picture caption="The same three versions, first as an ESchema, then as an EntityESchema: taskId appears in every version at once. A later version that tries to touch it is refused.">
  <IdPicture />
</Picture>

Why so strict? Because the id is how a saved task is found again. A
version that changed it would lose every task saved before it. With the
id fixed for all time, an old task upgrades to the latest shape and is
still the same task.

## Which one to write

Write an EntityESchema for a thing you keep many of, each found by its id:
tasks, boards, people. Write a plain ESchema for an object that has no id
of its own, like your app's settings, of which there is just one. You'll
save both kinds in [Entities](/std-toolkit/what-is-an-entity).

<Callout title="Remember">
  An EntityESchema is an ESchema plus an id field. The builder puts the id in
  every version, and no version may touch it.
</Callout>

Both kinds version an object with fields. But what about a value that
