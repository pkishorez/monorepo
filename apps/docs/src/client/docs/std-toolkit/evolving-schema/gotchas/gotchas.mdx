You've seen the whole of Evolving schema: versions, migrations, reads
that upgrade and writes that use the latest. It moves your migrations
from deploy day to read time, and that trade has a few sharp edges. This
page shows the one you'll meet first, then the rules that keep you clear
of the rest.

## A row from the future

Upgrades only go forward. New code reads every old row. But old code
can't read a row that new code wrote, because it has never heard of that
version.

You'll meet this in a browser. A user keeps a tab open from last week.
You ship a v2, and a v2 task reaches that tab. The code in it knows
nothing past v1.

Here both releases save tasks into one table. The table is just a place
to keep them for now; you'll meet it properly in
[StdTable](/std-toolkit/single-table-design). The right column reads the
board as the old release would.

The read doesn't guess, and it doesn't call the row bad data. It fails
with **OutdatedVersion**, which names the version it met and the latest
one it knows. That's how old code can tell that it, not the data, is out
of date.

## Telling outdated from broken

failure. `findOutdatedVersion` looks through any failure and gives back
the OutdatedVersion inside, or `undefined`.

Every other failure to read or write is an **ESchemaError**. That

which migration and why.

## The rules

Most of these the builder enforces. The rest are caught by your table's
[Snapshot](/std-toolkit/snapshot) test, as long as you have one.

- **A shipped version is forever.** Never edit v1's fields or its migration
  once rows exist. Add a version instead.
- **Never delete a migration.** Rows saved at v1 are still v1 on disk.
  Without the v1 → v2 step, they stop reading.
- **Migrations are pure.** No clock, no random numbers, no requests. The
  same row must read the same today, tomorrow and on every device.
- **One step per version.** Each migration handles only the version just
  before it. The chain does the rest.
- **A check only loosens on a shipped version.** Widening a bound is safe.
  Tightening one makes stored rows fail it, so it needs a new version, with
  a migration that makes old values pass.
- **A field's conversion is part of its version.** Changing how a shipped
  field converts, say from a string to a `Date`, needs a new version too.
  Nothing can see a conversion, so nothing catches this one for you.

## While you build

Nothing freezes a version until it ships. While you build a feature, edit
the newest version as much as you like. Just do it against the Memory
adapter, so a reload starts empty and a version you drop leaves no rows
behind.

<Callout title="Remember">
  New code reads every old row; old code fails with OutdatedVersion on a newer
  one. Never edit or delete a version once rows exist.
</Callout>
