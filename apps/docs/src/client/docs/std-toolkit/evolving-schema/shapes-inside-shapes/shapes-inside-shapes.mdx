Real data is nested. A task has a status, and a checklist of items. This
page shows how you put one versioned shape inside another, and what
happens when only the inner one changes.

## Nesting a shape

Every ESchema, of any kind, has a `schema`: a plain Effect Schema you can
use anywhere a Schema goes. To nest a shape, you use its `schema` as a
field, even inside `Schema.Array`.

Here `Task` holds a `Status`, which is a ValueESchema, and a list of
`Item`s, which are ESchemas. Release 2 gives `Status` a v2 that renames
`'todo'` to `'open'`. Look closely: `Task` itself gets no new version.

## Each level keeps its own version

When a task is stored, every nested shape is stored with its own `_v`:
the task, the status envelope and each checklist item. A read upgrades
each one through its own migrations, on its own.

  <NestedPicture />
</Picture>

That last point has a name: a **transitive change**. When a nested shape
evolves, every shape that holds it reads differently, even though their
own versions didn't move. It's what you want, since old statuses read as
new ones everywhere. But it means you can't change a shape without
thinking about who holds it.

## Which fields are shapes

Sometimes code needs to know if a field is a versioned shape, say to show
it in a tool. `eschemaOf` takes any Schema and gives back the ESchema it
is the `schema` of, or `undefined`.
