You now have two kinds of shape: objects with fields, and single values
like the theme. Real data mixes them. Your settings are an object, and the
theme is one of their fields. This page puts one versioned shape inside
another, and shows what happens when only the inner one changes.

## Nesting a shape

Every ESchema, of any kind, has a `schema`: the plain Effect Schema that
reads and writes it. To nest a shape, use its `schema` as a field.

```ts file=./components/settings.ts

```

`Settings` holds a `language` and a `theme`. The theme is the ValueESchema
from the last page. Look at the versions: `Theme` has a v2, but `Settings`
has only ever had v1. Settings never changed; its theme did.

The same works anywhere a Schema goes. A task's checklist could be
`Schema.Array(Item.schema)`, a list of versioned items.

## Each level keeps its own version

When settings are saved, each shape is stored with its own `_v`: the
settings object, and the theme's envelope inside it. A read upgrades each
one through its own migrations, on its own.

<Picture caption="Only Theme changed, so only the theme is upgraded. Settings still says v1, yet what it reads as has changed.">
  <NestedPicture />
</Picture>

That last point has a name: a **transitive change**. When a nested shape
gets a new version, every shape that holds it reads differently, though
their own versions never moved. Usually that's what you want: old themes
read as new ones everywhere. But it means a change to a small shape can
reach far. Before you add a version to it, look at who holds it.

The last lines use `eschemaOf`. It takes any Schema and gives back the
ESchema it is the `schema` of, or `undefined`. Tools use it to tell a
versioned field from a plain one.

<Callout title="Remember">
  A nested shape keeps its own version and upgrades on its own. Changing it

</Callout>
