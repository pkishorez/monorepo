Every app changes the shape of its data sooner or later. A task gets a
priority, a name gets split in two. This Part is about making that change
safely, and it starts with why it is hard at all.

## An API change is a moment

Say your server answers `GET /tasks`, and you add a `priority` to each task.
You change the server, you change the app that calls it, and you ship both.
From then on, every request and every response has the new shape.

The old shape is gone the moment the deploy finishes. Nothing that used it
is left anywhere. That's why changing an API feels easy: both sides move
together, at one point in time.

## Saved data stays

Data you save is different. A task saved in January sits in the database in
January's shape. In March your code expects a `priority`, but that row has
none. It wasn't there when the row was written, and nothing went back to add
it.

## Why this needs its own answer

Nothing is wrong with either shape. Each was right for the code of its day.
The trouble is that a database holds data from every day your app has ever
run, all at once.

An **evolving schema** is the answer std-toolkit gives: a shape that knows
every version it has ever had, and can read data saved under any of them.
