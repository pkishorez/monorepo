Everything so far assumed your rows carry a version. But you rarely start
with std-toolkit. More often you start with an app that already works, and
a database full of rows saved with no `_v` at all. This page brings those
rows along, with nothing to rewrite.

## A row with no version

What should a read do with a row that has no `_v`? std-toolkit's answer
is one rule: **a row with no version reads as v1**.

Not the latest version: the first. That's the only safe guess, because v1
is the shape your old code was writing. From v1, the row upgrades through
every migration, like any other v1 row.

## Adopt in two releases

So adopting is two steps, shipped one after the other. First, write down
the shape your rows already have as v1, and change nothing else:

```ts file=./components/task.ts

```

`TaskAdopted` is that first release. It has one version, so every old row
reads exactly as it did before. It changes nothing for your users, so it's
safe to ship alone.

Later releases add versions as usual: `Task` adds a priority, then
`done`. An old row with no `_v` reads as v1, and both migrations bring it
up to v3.

## v1 must match the rows you have

One thing is on you: v1's fields must be the fields your old rows really
have. std-toolkit can't check that ahead of time. If an old row doesn't
fit v1, its read fails loudly. It never guesses another shape.

So look at real rows before you write v1. If some lack a key, an ESchema
can't describe them, since it has no optional fields. Version the whole
object as a [ValueESchema](/std-toolkit/value-eschema) instead: it wraps
any Schema, optional keys included.

The rule holds for values too. A bare value with no envelope reads as v1,
so a theme saved as plain text keeps working once you version it.

## Rows already in a table

The no-version rule is about reading a value with an ESchema. A
[StdTable](/std-toolkit/single-table-design) is stricter: it writes `_v`
on every row it saves, and expects it on every row it reads.

A persistent table can still hold rows but no
[Stored contract](/std-toolkit/table-mode), say one set up before the
contract existed. Its first setup adopts it, once. It reads every row, and
each must be an entity the table declares and read under its ESchema. It
writes each row's index keys as it goes, then records the contract. A row
that doesn't fit stops setup with the reason `unadoptable`, naming the
row, and nothing is recorded. A disposable table in that state is wiped
instead.

<Callout title="Remember">
  A row with no version reads as v1. Ship the shape you already have as v1
  first, and make sure it matches the rows you really have.
</Callout>
