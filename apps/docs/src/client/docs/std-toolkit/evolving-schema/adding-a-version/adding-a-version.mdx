Your task shape has one version, and people have saved tasks with it. Now
tasks need a priority. This page adds it as a second version, so every
task saved before still reads.

## Release 2 wants a priority

Release 1 of your app saves tasks as `{ boardId, title }`. Release 2 wants
`{ boardId, title, priority }`. The tasks release 1 saved will still be in
the database when release 2 ships, with no priority at all.

You can't ask those rows to change. What you can do is tell the shape what
a missing priority should be.

## One evolve step

You add a version with `evolve`, between `make` and `build`. Here are both
releases' shapes side by side:


`evolve` takes three things:

1. **The version's name**, `'v2'`. Versions go in order: after v1 comes v2,
   and TypeScript won't let you skip one.
2. **What changed**, `{ priority: … }`. This is a **delta**: only the fields
   that are new or different. Every other field carries over as it was.
3. **The migration**, `(v1) => ({ ...v1, priority: 'low' })`. It gets a
   task in v1's shape and returns it in v2's.

So a task saved without a priority reads as `'low'`. Your code sees one
shape, `typeof Task.Type`, with `priority` in it. It never needs to know a
v1 ever existed.

## What a migration should be

A migration runs every time an old row is read, maybe on many machines,
for years. So keep it simple:

- **The same input gives the same output.** No clock, no random numbers,
  no network. The same old row must read the same way everywhere.
- **It handles every old value.** It gets anything v1 could have stored.
  If it throws, the read fails.

<Callout title="Remember">
  Add a version; never edit one you have shipped. Old rows are upgraded when
  they are read, and written in the latest shape only when they are saved.
</Callout>
