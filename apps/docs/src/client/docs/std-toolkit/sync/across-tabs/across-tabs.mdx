People open your board in three tabs, close the laptop, and come back on a
train with no signal. So far the copy has lived in one tab's memory: gone on
reload, and each tab fetching for itself. This page moves it somewhere every
tab can share, and shows what happens offline.

## Where the copy lives

A Std Sync keeps its copy wherever its **Sync adapter** says. By default
that's memory. Give it `Sync.idb()` instead:

```ts
import { createStdSync } from '@kestack/std-toolkit/sync';
import { Sync } from '@kestack/std-toolkit/sync/idb';

const app = createStdSync({ name: 'board', store: Sync.idb() });
```

Now the copy is in IndexedDB, shared by every tab of your app in this
browser. It outlives a reload, and the tabs agree.

## One tab reads for all

If every tab polled the Backend, three tabs would cost three times as much.
So each reading job, the global strategy or one Window's, has a
**Leadership**: one tab holds it, and the others wait.

The leading tab stores what it reads in the shared copy, then rings the
**Doorbell**. Every tab hears it and reads that Collection again from the
copy. The Doorbell carries no rows; it only says "look again".

When the leading tab closes, another takes over from the saved cursor.
Different tabs may lead different Windows.

`Sync.idb` uses Web Locks for Leadership and a BroadcastChannel for the
Doorbell. Where a browser lacks one, every tab simply reads for itself.

## Offline

A Collection opens from its copy before any network call, so the board is
there at once, even with no signal. Each strategy then resumes from its
saved cursor.

When a fetch fails, it tries again after a growing delay, and the copy stays
on screen. Once the network is back, reading picks up where it stopped.

An edit is different. A Mutation Callback calls the Backend directly. If it
can't, the edit is rolled back, rather than shown as saved when it isn't.
Edits that wait offline and send later aren't in this version.

## A tab older than the data

You ship release 3 of `Task`, which adds `done`. A tab opened yesterday is
still on release 2. The new release saves a task at v3, and the old tab's
copy receives it.

The old tab can't read a version it has never heard of. That is the
[`OutdatedVersion`](/std-toolkit/gotchas) you met in Evolving schema, and
here it has a name: an **Outdated Application**. It isn't bad data; the tab
is behind. So Sync skips that task, reports it once, and stops reading that
scope until a reload brings the new code.

## Signing out

Nothing is deleted on its own. Put the user's id in the Std Sync's name, so
one person never sees another's rows. On sign-out:

```ts
await app.dispose();
await Sync.idb.remove(`board:${userId}`);
```

`Sync.idb.list()` lists every Std Sync stored in this browser. On a shared
or sensitive device, use `Sync.memory()`, and nothing touches the disk.
