You've seen the idea by hand: a copy on the device that asks for what
changed after its cursor. **Std Sync** does that work for you, and gives
your screen the copy as something it can query.

## A Std Sync and its Collections

You start with a Std Sync: one named group of Collections, kept in one place
on the device.

```ts
import { createStdSync, strategy } from '@kestack/std-toolkit/sync';

const app = createStdSync({ name: 'board' });
```

Then you add a **Collection** for each kind of thing, with the same schema
your table uses. The schema comes first, so everything else is typed from
it.

```ts
const tasks = app.collection(Task, {
  sync: {
    global: strategy.oldToNew({
      fetch: ({ after }) => api.changesSince(after),
      pollEvery: '5 seconds',
    }),
  },
  onInsert: (items) => Effect.forEach(items, (item) => api.insertTask(item)),
  onUpdate: ({ current, updates }) => api.updateTask(current, updates),
  onDelete: ({ current }) => api.deleteTask(current),
});
```

`tasks` is a TanStack DB Collection. You query it like any other, and its
rows are your schema's latest values. Behind it, the device keeps its copy,
the **Sync Replica**: what the Backend confirmed, and nothing else.

That config has two halves. `sync` says how the copy reads the Backend.
`onInsert`, `onUpdate` and `onDelete` say how edits get back to it.

## Reading

`sync` holds a **Sync Strategy**. This one asks the Backend for everything
changed after the newest task it has, then asks again every five seconds:
the question from [How sync works](/std-toolkit/how-sync-works), on a timer.
[Strategies](/std-toolkit/strategies) shows the other choices.

## Writing

When your screen adds, edits or deletes a row, the change shows at once, as
an **Optimistic Entity**. It isn't in the Sync Replica yet: the Backend
hasn't confirmed it.

Then Sync calls your **Mutation Callback**. It gets plain values, in today's
shape, sends them to the Backend, and returns what the Backend saved. That
answer goes into the Sync Replica, and the optimistic row is dropped. Since
the saved row is already there, nothing flickers.

If the callback fails, the change is rolled back. The screen never shows as
saved what wasn't.

Because the copy keeps whichever `_u` is newer, it doesn't matter whether a

same.

## When you're done

`await app.dispose()` stops a Std Sync. Writes on their way get a few
seconds to land, and its stored data is kept for next time.

<Callout title="Remember">
  A Collection shows the device's copy of what the Backend confirmed, plus your
  edits on top until the Backend confirms them too. A Mutation Callback takes
  values and returns the saved Entity.
</Callout>
