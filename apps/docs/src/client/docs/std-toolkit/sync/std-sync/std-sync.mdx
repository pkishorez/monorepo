Your tasks live in a table on the server. Your screen is in a browser. This
page connects the two: a Collection you query like any TanStack DB
Collection, kept fresh from the server, with a copy on the device.

## Why not just fetch?

Fetching on every screen works, until it doesn't. The page is blank while
it loads. It goes empty offline. Two tabs show two different answers. And
every edit waits for the server before it shows.

Sync fixes those with a local copy. The server stays the **Backend**: the
one authority. The device keeps a **Sync Replica**, a copy of what the
Backend confirmed, and the screen reads from that.

## A Std Sync and its Collections

You start with a **Std Sync**: one named group of Collections, kept in one
place.

```ts
import { createStdSync, strategy } from '@kestack/std-toolkit/sync';

const app = createStdSync({ name: 'board' });
```

Then you add a **Collection** for each kind of thing, with the same schema
your table uses. The schema comes first, so the rest is typed from it.

```ts
const tasks = app.collection(Task, {
  sync: {
    global: strategy.oldToNew({
      fetch: ({ after }) => api.changesSince(after),
      pollEvery: '5 seconds',
    }),
  },
  onInsert: (items) => Effect.forEach(items, (item) => api.insertTask(item)),
  onUpdate: ({ current, updates }) => api.updateTask(current, updates),
  onDelete: ({ current }) => api.deleteTask(current),
});
```

`tasks` is a TanStack DB Collection. You query it the way you'd query any
other, and its rows are your schema's latest values.

## Reading: a strategy

`sync` says how the Collection reads the Backend. Here, one **Sync
Strategy** reads everything changed after the newest task it has, then asks
again every five seconds. [Strategies](/std-toolkit/strategies) covers the
choices.

Rows arrive in their stored shape, at whatever version they were saved in.
The Collection shows them at the latest version, migrated as they're read,
just like a table read. Your screen never sees an old shape.

## Writing: Mutation Callbacks

`onInsert`, `onUpdate` and `onDelete` are **Mutation Callbacks**. When your
screen changes the Collection, the change shows at once, as an **Optimistic
Entity**. The callback sends it to the Backend and returns what the Backend
saved.

That answer goes into the Sync Replica, so the row doesn't flicker back
while it waits for the next fetch. If the callback fails, the change is
rolled back.

## Two copies, one winner

Every Entity carries `_u`, its update key, and a newer `_u` wins. A stale
or repeated Entity is ignored. So it doesn't matter whether a task arrives
from a fetch, a callback, or another tab: the copies end up the same.

When you're done with a Std Sync, `await app.dispose()` stops it. Writes on
their way get a few seconds to land, and its stored data is kept.

<Callout title="Remember">
  The Backend is the authority. A Collection shows the device's copy of what it
  confirmed, plus your edits on top until the Backend confirms them too.
</Callout>

How the Collection reads the Backend is up to its strategy. Next,
[Strategies](/std-toolkit/strategies): oldest first, newest first, or
only what's on screen.
