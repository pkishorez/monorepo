Your tasks now live in one table, on a server, behind an adapter. But the
people using your board are in a browser. This Part is about the last step:
getting those tasks onto a screen, and keeping them fresh.

## Why not just fetch?

The obvious way is to fetch the tasks every time a screen opens. It works,
until it doesn't:

- the screen is blank while it loads;
- with no signal, it is empty;
- two open tabs can show two different answers;
- an edit waits for the server before it shows.

Each of these has the same cure: keep a copy on the device, and show that.

## The big picture

The server keeps the table. It is the **Backend**: the one authority on what
is saved. Each device keeps a **copy** of what the Backend confirmed, and
the screen reads from the copy. So the screen opens at once, even offline.

The hard part is keeping the copy fresh without fetching everything again.
std-toolkit already has what it needs. Every save stamps an entity with
`_u`, its **update key**: a ULID, which sorts by the time it was made. So
the newest save always has the largest `_u`.

That gives the copy one simple question to ask the Backend: "what changed
after the newest `_u` I have?" That `_u` is the copy's **cursor**.

## Newer wins

A task can reach the copy more than once, or out of order. A pull may repeat
one, another tab may pass on what it read, and your own edit comes back from
the Backend. One rule makes all of that safe: **a newer `_u` wins**. An
entity whose `_u` is older than, or the same as, the one already held
changes nothing.

So it never matters where a task came from, or in what order. Every copy
ends up the same.

## Old rows arrive in today's shape

The copy reads with the same schema as the table. So a task saved long ago,
at v1, reaches the screen in today's shape, upgraded on the way, just as a
table read upgrades it. Your screen never sees an old shape.
