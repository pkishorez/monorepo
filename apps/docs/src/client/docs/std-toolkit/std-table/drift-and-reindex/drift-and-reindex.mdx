The last page added `byPriority`. New tasks show up in it. The tasks
saved last month don't, until something writes their keys. On a
persistent table, setup does that for you, before the new code opens the
table. This page shows why those rows go missing, and what setup does
underneath.

## Why old rows go missing

An index key is written when a row is saved. A task saved before
`byPriority` existed was saved without a `byPriority` key. So a
`byPriority` query never sees it.

You might expect this to heal itself, the way an old shape does. A row
saved at v1 is upgraded when it's read, as [Reading and
writing](/std-toolkit/reading-and-writing) showed. But an index can't
work that way: the query never reaches the row, so there's nothing to
upgrade. Those rows need their keys written.

## Setup writes them

You don't declare anything for this. When setup compares your table with
its [Stored contract](/std-toolkit/table-mode), a new or changed index
shows up as a change that requires a reindex. On a persistent table,
setup then scans the table and rewrites each row whose index keys are
out of date, all before the table opens:

```ts
yield * SQLite.setup(table, { database, mode: 'persistent' });
// { kind: 'applied', reindexed: ['Task'], changes: [...] }
```

It keeps no progress. The new contract is recorded only after the scan,
so a setup that stops part-way leaves the old one, and the next setup
reindexes again. That's safe, because writing the same keys twice
changes nothing.

On DynamoDB, setup adds the new global secondary index first, then
reindexes. A disposable table skips all this: setup wipes it and starts
fresh.

The rest of this page is what that reindex does, one row at a time.

## Drift: finding the gap

**Drift** is the gap between the keys a row has and the keys this release
would give it. `table.drift(item)` checks one stored row:

```ts
table.drift(item); // an Effect of { drifted, currentForm }
```

`drifted` says whether the keys differ. `currentForm` is the row as this
release would store it, with every index key filled in.

An older `_v` alone isn't drift. The row's keys are the same, and a read
upgrades it anyway.

## Reindex: filling it

`table.reindex(row)` writes a row back with the keys you give it. Setup
gives it the stored row with only its keys replaced, so the value and its
version stay as they were. It's careful about what it touches:

- It keeps the row's update stamp, `_u`. The value didn't change, so
  nothing that syncs should think it did.
- It tells no subscriber. To them, nothing happened.
- If someone saved the row since it was read, it fails with
  `ReindexConflict` rather than overwrite the newer write. Setup reads the
  row again and retries.

<Callout title="Remember">
  A new index only knows the rows saved after it. On a persistent table, setup
  finds the rest with drift and writes their keys with reindex, before the table
  opens, without changing their value or their stamp.
</Callout>
