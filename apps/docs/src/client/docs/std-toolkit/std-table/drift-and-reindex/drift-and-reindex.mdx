You add an index, and new tasks show up in it. The tasks saved last month
don't. By the end of this page you'll find those rows and bring them in,
without touching their values.

## Why old rows go missing

An index key is written when a row is saved. A task saved before
`byStatus` existed was saved without a `byStatus` key, so a `byStatus`
query can't see it.

A schema change heals itself on read, as [Adding a
version](/std-toolkit/adding-a-version) showed. An index can't: the query
never reaches the row to read it. Those rows need their keys written.

## Drift

**Drift** is the gap between the keys a row has and the keys this release
would give it. `table.drift(item)` checks one stored row:

```ts
const { drifted, currentForm } = yield * table.drift(item);
```

`drifted` says whether the keys differ. `currentForm` is the row as this
release would store it.

A row that only has an older `_v` has not drifted. Its keys are the same,
and a read upgrades it anyway.

## Reindex

`table.reindex(currentForm)` writes that current form back. It changes
the row's index keys, and nothing else that matters:

- it keeps the row's update stamp, `_u`, because the value didn't change;
- it sends no Change Notice, so subscribers aren't told about a non-event;
- if someone saved the row since you read it, it fails with
  `ReindexConflict` instead of overwriting the newer write.

You don't usually run this by hand. A snapshot sees a new index as a
change that needs a backfill, and on IndexedDB setup reindexes for you.
The rest of this Part covers that.

<Callout title="Remember">
  A new index only knows rows saved after it. drift finds the rest, and reindex
  writes their keys without changing their value or their stamp.
</Callout>
