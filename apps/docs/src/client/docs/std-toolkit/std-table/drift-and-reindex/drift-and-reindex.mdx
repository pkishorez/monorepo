The last page added `byPriority`. New tasks show up in it. The tasks
saved last month don't. This page finds those rows and brings them in,
without changing a single value.

## Why old rows go missing

An index key is written when a row is saved. A task saved before
`byPriority` existed was saved without a `byPriority` key. So a
`byPriority` query never sees it.

You might expect this to heal itself, the way an old shape does. A row
saved at v1 is upgraded when it's read, as [Reading and
writing](/std-toolkit/reading-and-writing) showed. But an index can't
work that way: the query never reaches the row, so there's nothing to
upgrade. Those rows need their keys written.

## Drift: finding the gap

**Drift** is the gap between the keys a row has and the keys this release
would give it. `table.drift(item)` checks one stored row:

```ts
table.drift(item); // an Effect of { drifted, currentForm }
```

`drifted` says whether the keys differ. `currentForm` is the row as this
release would store it, with every index key filled in.

An older `_v` alone isn't drift. The row's keys are the same, and a read
upgrades it anyway.

## Reindex: filling it

`table.reindex(currentForm)` writes that current form back. It's careful
about what it touches:

- It keeps the row's update stamp, `_u`. The value didn't change, so
  nothing that syncs should think it did.
- It tells no subscriber. To them, nothing happened.
- If someone saved the row since you read it, it fails with
  `ReindexConflict` rather than overwrite the newer write.

A whole backfill is a walk over the table: check each row, repair the
ones that drifted.

You won't usually run this by hand. A [snapshot](/std-toolkit/snapshot)
flags a new index as needing a backfill, and on IndexedDB, setup runs the
reindex for you.

<Callout title="Remember">
  A new index only knows the rows saved after it. drift finds the rest, and
  reindex writes their keys without changing their value or their stamp.
</Callout>
