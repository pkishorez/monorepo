Moving a task to another board takes two writes: add it there, remove it
here. If only one lands, the task is lost or doubled. By the end of this
page you'll save both as one change.

## All or nothing

A key can't change in an update, as [Keyed
entity](/std-toolkit/keyed-entity) said. So a move is an insert on the
new board and a delete on the old one.

A **transaction** saves them together. Either every write lands, or none
of them does.

## Ops, then transact

Every write you've used has an `Op` twin: `insertOp`, `getAndUpdateOp`,
`deleteOp`, `restoreOp`. An op prepares the write without saving it.
Then `table.transact` saves the list:


Every write in a transaction gets the same update stamp, `_u`. So a
device that syncs later sees the move as one change, not two.

When a transaction is refused, it fails with `TransactFailed`, and says
which op refused and why. Nothing is written.

## Checks

Sometimes a batch depends on a row it doesn't change: "add this task, but
only if its board isn't archived". A check op asserts something without
writing:

- `getAndCheckOp(key, (current) => …)` holds when your function says so;
- `existsOp` and `notExistsOp` hold when the row is there, or isn't;
- `unchangedOp(entity)` holds when nobody saved that row since you read
  it.

If a check fails, the whole batch is refused, just like a refused write.

## Limits

A transaction follows DynamoDB's rules on every adapter:

- at most 100 ops;
- each row at most once;
- every op from the same table.

Break one, and it's refused before anything is written, even on Memory.
So a batch that works in your tests works in production too.

## scan

One more table-wide call. `table.scan()` streams every row in the table,
of every kind, as it is stored. The rows are untyped, since no one shape
fits them all. It's what a backfill walks, as [Drift and
reindex](/std-toolkit/drift-and-reindex) showed, and it's how the Live
Tables on these pages draw their left column.
