Setup refuses a breaking change, but only when it finally meets the data:
on a server after a deploy, or on a reader's phone. You'd rather find out
in a test, before anyone merges the change. This page gives you that
test.

## Why the types can't catch it

Say you shipped Task at v1, and people saved tasks. Now, instead of
[adding a version](/std-toolkit/adding-a-version), you write `priority`
straight into v1.

It compiles. Your tests pass. And every task saved at v1 no longer reads,
because none of them has a priority.

TypeScript only knows today's code. It doesn't know what you shipped.

## A snapshot remembers what you shipped

A **table snapshot** is that missing memory. It's plain JSON describing
your table: its keys and indexes, the entities declared on it, and every
version of every shape they use.

Compare the snapshot you shipped with the one you're about to ship, and
every difference gets a verdict. They're the four you met on [Table
mode](/std-toolkit/table-mode): safe, requires-reindex, breaking and
unverifiable.

## capture and diff

`TableSnapshot` comes from `@kestack/std-toolkit/schema/snapshot`. Three calls do
the work:

```ts
const changes = TableSnapshot.diff(shipped, TableSnapshot.capture(table));
console.log(TableSnapshot.renderChanges(changes));
```

`capture` reads a table and every entity declared on it into a snapshot.
`diff` compares two snapshots and returns one change per difference, each
with its verdict in `impact`. `renderChanges` writes them out for a
person.

## The test that ships with your table

You don't call `diff` by hand. You keep the shipped snapshot as a file in
your repo, and one test compares against it. `expectTableShippable` comes
from `@kestack/std-toolkit/db/testing`, and needs `vitest`:

```ts
import { expectTableShippable } from '@kestack/std-toolkit/db/testing';
import { it } from 'vitest';
import { table } from '../src/table.js';

it('keeps the table safe to ship', async () => {
  await expectTableShippable(table, './fixtures/table.snapshot.json');
});
```

It takes the table, the path of the snapshot file, and optionally how many
rows to generate for the upgrade check. It fails, listing every reason,
when a change is breaking against the file, when a stored version no
longer upgrades to the latest, when a migration would change a row's id
or partition key, or when the file is out of date.

`vitest -u` writes the new snapshot, but only for a change that is safe
or needs a reindex, which setup runs itself. Nothing accepts a breaking
change. Undo the edit and add a version, or move the data to a new table
with a [table migration](/std-toolkit/table-mode).

You only need this test for a persistent table. A table kept only in
disposable storage may change freely, so it needs none.

A test can be skipped, so it isn't the only check. Setup compares against
the Stored contract, and a deploy compares against what you last
deployed. The test is just the earliest, and the cheapest place to find
out.

<Callout title="Remember">
  Commit a snapshot and test against it. A breaking change then fails in CI,
  long before it can strand a single row.
</Callout>
