Setup refuses a breaking change, but only once it meets the data. You'd
rather know in a test, before anyone reviews the change. By the end of
this page you'll have that test.

## Why types can't catch it

Say you shipped Task at v1, and rows were saved. Now you write a
`priority` straight into v1, instead of adding a v2. It compiles. Your
tests pass. And every row saved at v1 no longer reads, because none of
them has a priority.

The types only know today's code. They don't know what you shipped.

## A picture of the table

A **table snapshot** is that missing memory. It's plain JSON describing
your table: its keys and indexes, the entities bound to it, and every
version of every shape they use.

Compare the snapshot you shipped with the one you're about to ship, and
each difference gets a verdict.

<Picture caption="A new version is safe. An edited version is breaking. A new index needs a backfill. Only the line that changed moves.">
  <DiffPicture />
</Picture>

The verdicts are the same four that setup uses, as [Table
mode](/std-toolkit/table-mode) explained: safe, requires-backfill,
breaking and unverifiable.

## capture and diff

`TableSnapshot` comes from `@kestack/std-toolkit/snapshot`:

```ts
const changes = TableSnapshot.diff(accepted, TableSnapshot.capture(table));
console.log(TableSnapshot.renderChanges(changes));
```

`capture` reads a table and every entity bound to it. `diff` compares two
snapshots and returns one change per difference. `renderChanges` writes
them out for a person to read.

## The test that ships with your table

You don't call `diff` by hand. You keep the shipped snapshot as a file in
your repo, and one test compares against it:

```ts
import { expectTableShippable } from '@kestack/std-toolkit/snapshot/vitest';
import { it } from 'vitest';
import { table } from '../src/table.js';

it('keeps the table safe to ship', async () => {
  await expectTableShippable(table, './fixtures/table.snapshot.json');
});
```

The test fails, listing every reason, when:

- a change is breaking against the file;
- a stored version of a shape no longer upgrades to the latest;
- a migration would move a row to another key;
- the file is out of date.

Run `vitest -u` to write the new snapshot. It only writes it when the
change keeps stored rows readable. Nothing accepts a breaking change:
undo the edit and add a version, or move the data to a new table name.

A test can be skipped, so it isn't the only check. Setup compares against
the Stored contract, and a deploy guard compares against what you last
deployed. The test is just the earliest.

<Callout title="Remember">
  Commit a snapshot and test against it. A breaking change fails in CI, long
  before it can strand a single row.
</Callout>
