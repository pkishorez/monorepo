## One table, every kind

The usual way is a table per kind of thing: one for boards, one for
tasks, one for settings. std-toolkit keeps them all in **one** table.
That's called **single-table design**, and it's how DynamoDB is meant to
be used.

It works because every row is found by its key, not by which table it is
in. A row has two keys:

- the **partition key** (`pk`) groups rows that belong together;
- the **sort key** (`sk`) orders them inside that group.

## A StdTable

A **StdTable** is that one table, described once. You give it a name and
the names of its two key columns:

```ts file=./components/app.ts

```

`'app'` is its logical name. It's unique in your app, and it is how an
adapter's layer finds this table.

Then each kind is bound to it. You've seen `table.entity(...)` and
`table.singleEntity(...)` already. Each binding says which value fields
build the keys; you never write a `pk` or `sk` by hand.

## How keys are made

std-toolkit derives the physical keys from your value:

| Kind     | pk          | sk       |
| -------- | ----------- | -------- |
| Board    | `Board`     | `work`   |
| Task     | `Task#work` | `t1`     |
| Settings | `Settings`  | `single` |

The partition key starts with the kind's name. A task's partition adds
its `boardId`, because the task said `.primary({ pk: ['boardId'] })`. The
sort key is the entity's id. A single entity has one fixed sort key.

All the rows with one partition key are an **item collection**: all the
tasks on one board. A `query` reads one item collection, in sort key
order. That's why listing a board is one fast read.

Every stored row also carries its kind in `_e`, its **type tag**. So
reading a row back, std-toolkit knows which shape to decode it with.
