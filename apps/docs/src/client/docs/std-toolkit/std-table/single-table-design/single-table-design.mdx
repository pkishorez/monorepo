## The problem with a table per kind

The usual way is a table for each kind of thing: one for boards, one for
tasks, one for settings.

Each of those tables is one more thing to set up, deploy, back up and
keep in step with your code. Each needs its own checks when a shape
changes. And a screen that shows a board with its tasks reads from two
places.

## One table for everything

std-toolkit keeps every kind of thing in **one** table. That's called
**single-table design**. It's how DynamoDB is meant to be used, and it
works just as well on SQLite or in the browser.

There's one place to set up, one place to check when a shape changes, and
one stream of changes to sync. The rest of this page answers the obvious
question: if everything is in one table, how do the kinds stay apart?

## Keys tell the kinds apart

Every row is found by two keys, not by which table it sits in:

- the **partition key**, `pk`, groups rows that belong together;
- the **sort key**, `sk`, orders the rows inside that group.

The table's name, `'board'`, is how an adapter finds it later. Then each
kind is declared on it, as you saw in the Entities Part. The table is
declared in one place, with every kind it holds, and the built table
carries each one under its name: `table.Task`.

## What the keys look like

Here's where each row lands:

| Kind     | pk          | sk       |
| -------- | ----------- | -------- |
| Board    | `Board`     | `work`   |
| Task     | `Task#work` | `t1`     |
| Settings | `Settings`  | `single` |

The partition key starts with the kind's name. A Task adds its `boardId`,
because it was declared with `e.primary({ pk: ['boardId'] })`. The sort key is
the entity's id, and a single entity has one fixed sort key.

All the rows that share a partition key are an **item collection**: every
task on one board. A `query` reads one item collection, in sort key
order. That's why listing a board is one fast read.

Each stored row also carries its kind in `meta._e`. Reading a row back,
std-toolkit knows which shape to decode it with.
