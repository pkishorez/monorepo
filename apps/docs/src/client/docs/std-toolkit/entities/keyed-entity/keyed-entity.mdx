You have `task`, an entity made of a shape, a key and a table. Now let's
use it the way a task list does: save tasks, find them, change them and
delete them.

## Many of a kind, found by a key

Tasks come many at a time, so each needs a key you can find it by. That's
what makes `task` a **keyed entity**.

You chose the key when you declared the shape on the table:

```ts
StdTable.make('board')
  .primary('pk', 'sk')
  .entity(Task, (e) => e.primary({ pk: ['boardId'] }))
  .build();
```

`boardId` groups tasks by board, and the id field, `taskId`, picks one
task in the group. So a task's key is `{ boardId, taskId }`, and that's
all you ever pass to find it.

What each one does:

- `insert` saves a new task. If one with the same key exists, it fails and
  keeps the first. Nothing is overwritten by accident.
- `get` finds one task by its key, or gives you `null`.
- `query` lists the tasks under one board, in key order. `'>=': null`
  means "from the start". It returns a page of up to 100; pass a `limit`
  for more or fewer.
- `getAndUpdate` reads the task, then saves only the fields you name. Pass
  a function instead, and it's given the current value.
- `delete` marks the task deleted. That's next.

A task's key can't change in an update. To move a task to another board,
you delete it and insert it again; [Transactions](/std-toolkit/transactions)
makes that one step.

## A delete leaves a tombstone

`delete` doesn't erase the row. It leaves a **tombstone**: the same task,
with `_d: true`. A screen showing the board, or a phone holding a copy,
needs to hear that the task went away. A tombstone is how it hears.

So `get` and `query` return deleted tasks too, unless you pass
`{ excludeDeleted: true }`. `restore` brings a deleted task back. And when
you truly mean it, `hardDelete` removes the row for good. It asks you to
type `'I KNOW WHAT I AM DOING'`, on purpose.
