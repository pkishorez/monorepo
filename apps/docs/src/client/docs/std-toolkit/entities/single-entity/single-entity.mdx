Tasks come many at a time, each with a key. Your app's settings don't:
there's exactly one set, and every screen wants to read it from the very
first run. This page keeps that kind of thing.

## Always there, from the first read

With a keyed entity, you insert first and read after. Settings can't work
that way. Code everywhere reads them, and none of it should have to ask
"have they been saved yet?"

A **single entity** answers with a default. Until something is saved, a
read gives you the default, and nothing is written to the table.

</Picture>

## Binding it

Settings have no id, so the shape is a plain [ESchema](/std-toolkit/eschema),
not an `EntityESchema`. You declare it with `singleEntity`, in the same table
as your tasks, and give it a default:

```ts file=./components/settings.ts

```

There's no key to pass: there's only one record, and every call works on
it.

## The calls

- `settings.get()` always gives you a value: the saved one, or the
  default. Never `null`.
- `put` saves the whole record, every field.
- `getAndUpdate` saves only the fields you name, merged into what is there
  now. Before the first save, "what is there now" is the default.
- `reset` saves the default back, as a real record.

There's no delete. A record that always has a value can't go away. A
reset is saved like any other write, so a screen or a device holding a
copy hears about it.
