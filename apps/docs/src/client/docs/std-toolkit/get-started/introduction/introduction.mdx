std-toolkit is for the data your app saves. This page is the whole story
in one read: the problem, the idea behind the answer, and the five Parts
that build it. No API yet, just the shape of things.

## Data outlives code

Think about an API first. You change what a call takes or returns, you
update the code that calls it, and you ship both. The change happens at
one moment, and after that moment everyone agrees again.

Saved data doesn't work like that. A task saved in January sits in the
database in January's shape. Your code changes in March, and the task is
still there, in the old shape, long after the code that wrote it is gone.
Change the shape of a task, and every task already saved no longer fits.

The usual fixes all hurt. A script rewrites every row on each deploy. Or
a `task.priority ?? 'low'` hides at every place that reads a task, forever.
Or you stop changing the shape at all.

## The idea: keep every version

std-toolkit takes another way. You describe a task once, and you keep
every version of that description. Each saved task carries the version it
was saved in. When your code reads an old task, it's upgraded on the way
in, one small step at a time, to today's shape. Writes always use today's
shape. Nothing is rewritten in bulk.

## Five Parts, one on the next

Everything else in std-toolkit builds on that idea, one layer at a time.
The docs follow the same order.

<Picture caption="A task travels down the five layers. Each one adds one thing: versions, a key, a place in one table, a database, and a copy on every screen.">
  <LayersPicture />
</Picture>

1. **[Evolving schema](/std-toolkit/why-evolving-schema).** A shape that
   remembers every version of itself, and upgrades old data as it's read.
   Everything else is built on it.
2. **[Entities](/std-toolkit/what-is-an-entity).** A shape, plus a key and
   a place to live, becomes something you can save, find, change and
   delete. Many of a kind, like tasks, or exactly one, like settings.
3. **[StdTable](/std-toolkit/single-table-design).** Tasks, boards and
   settings all share one table, told apart by their keys. A snapshot
   catches a breaking change in a test, before it reaches real data.
4. **[Adapters](/std-toolkit/what-is-an-adapter).** The same table runs in
   memory, in the browser's IndexedDB, in SQLite or in DynamoDB. Your code
   never names a database; one line picks it.
5. **[Sync](/std-toolkit/how-sync-works).** The server keeps the table, and
   each screen keeps a fresh copy: shared across tabs, usable offline, and
   always in today's shape.

You can stop after any Part and have something useful. Most apps start
with the first two.
