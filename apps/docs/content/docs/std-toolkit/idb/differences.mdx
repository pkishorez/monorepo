title: Differences
description: The honest diff between the browser adapter and its SQLite and DynamoDB siblings — where it runs, no registry, transactions, consistency — and when to reach for it.
---

Three siblings share one model, so the interesting part is where the browser adapter diverges. The shared contract — entity services, key derivation, envelopes, range queries, sk-as-cursor pagination, tombstone deletes, optimistic writes — genuinely is identical. The differences live at the edges, and each is a runtime being honest about its own physics. Verified against the adapter source.

## Where it runs

**idb runs in the browser, and only there.** It needs `globalThis.indexedDB`; on a bare Node process there's nothing to open, and the first Effect fails with `openFailed`. That's the point of the adapter, not a limitation — it's the _client_ member of the family. DynamoDB and SQLite are server- and edge-side; idb is the store on the user's machine, which is why it's the natural companion to [tanstack-sync](/docs/std-toolkit/tanstack-sync)'s offline storage. One set of entity definitions, a server adapter on one side and idb on the other, sync moving sorted items between them.

## No registry — the table is the surface

**SQLite and DynamoDB assemble an `EntityRegistry`; idb does not.** The Table absorbed that role. You define entities directly from the table (`table.entity(Message)`, `table.singleEntity(Settings)`), and the table itself carries `setup()` and `transact()`. There's no separate object to register entities into and thread through your app — you keep the references the builders return, and the table already knows about them because building an entity registers it back.

The one ergonomic consequence: there's no name-based lookup like `registry.entity('Message')`. Hold the `messages` and `channels` references from where you defined them and import those.

## Provisioning: runtime, and auto-versioned

**idb provisions itself at runtime, like SQLite — but through IndexedDB's version machinery.** `table.setup()` is idempotent: it creates the object store and adds any missing indexes, a no-op once complete. The twist is that IndexedDB only creates stores and indexes inside a versioned upgrade, so `setup` bumps the database version itself when something's missing — you never name a version. It also converges across tabs: if another tab wins the upgrade, `setup` rechecks and settles rather than erroring. DynamoDB, by contrast, provisions out-of-band through IaC on AWS's timeline.

## Consistency

**idb is strongly consistent and read-your-writes**, exactly like SQLite — one database on one machine, every read observes every prior write, through the primary key and through every [secondary index](/docs/std-toolkit/idb/indexes). There is no consistency knob.

**DynamoDB's consistency is a spectrum you manage** — eventually consistent reads by default, an opt-in `ConsistentRead` on `get`, and GSI queries that are always eventual. As with SQLite, this is the difference you feel first in tests: assertions that need retry-until-visible on DynamoDB pass immediately on idb. Don't let strong-consistency habits leak into code that will also run against GSIs.

## Transactions: buffered ops, like DynamoDB — not SQLite's interactive block

This is where idb sides with DynamoDB against SQLite. IndexedDB has no interactive begin/commit you can run arbitrary reads and branches inside, so idb takes the **buffered-ops** shape:

**idb — declare the writes, then commit.** Entities build deferred ops (`insertOp`, `getAndUpdateOp`, `deleteOp`, `restoreOp`), and `table.transact([...ops])` applies the batch in one native IndexedDB readwrite transaction, all-or-none. Write-only: you cannot read, branch, or compute inside the transaction — the batch is data, not code.

```ts
const channelOp =
  yield *
  channels.insertOp({
    channelId: 'C-standup',
    name: 'standup',
    topic: '',
  });
const firstMessageOp =
  yield *
  messages.insertOp({
    messageId: yield * nextUlid,
    channelId: 'C-standup',
    authorId: 'U-ada',
    body: 'kicking off',
  });

yield * table.transact([channelOp, firstMessageOp]);
```

Each op carries an optimistic `expectedU` the transaction re-checks per key; any violation aborts the whole thing with `conditionFailed` and applies nothing. Broadcasts fire only after commit, in op order. This is the same all-or-none `transact(ops)` shape every adapter exposes — a batch of pre-built ops, never a read-inside `transaction(effect)` (no adapter offers interactive transactions). If you need read-decide-write to be atomic, you express the decision as the op's optimistic guard rather than as code inside the transaction.

The read-modify-write itself is spelled **`getAndUpdate`** (like SQLite, not DynamoDB's expression `update`): it reads, merges your partial, and writes back guarded on the `_u` it read, retrying on conflict (default 3) before failing. `lastWriteWins: true` drops the guard.

## Query surface

The sort-key operators are `<`, `<=`, `>`, `>=`, and `beginsWith`, with nullable cursors on the comparison operators. Pass no `limit` and a query returns up to 100 rows. There's no page-truncation cap like DynamoDB's 1 MB `LastEvaluatedKey`; a page is exactly what you asked for, and `queryStream` runs the cursor-until-exhausted loop identically to the other adapters.

## Deletes and destructive escape hatches

`delete` is a tombstone on every adapter — `_d` flips, `_u` re-stamps, the row stays readable for sync consumers, and `restore` revives it. The _hard_ escape hatches:

- **`entity.hardDelete(key, 'I KNOW WHAT I AM DOING')`** physically removes one record by its primary key.
- **`dangerouslyRemoveAllItems('I KNOW WHAT I AM DOING')`** removes every row at its scope: the complete store when called on a table, or only that entity's records when called on an entity.

The warning is the same everywhere: hard deletion erases the tombstone, so anything syncing from the store never learns the row died. Reach for it in tests and cleanup, nowhere near synced data.

## Errors

Same ergonomics, own vocabulary: every idb operation fails with `IdbError`. The variants reflect the runtime — driver failures (`openFailed`, `setupFailed`, `getFailed`, `putFailed`, `deleteFailed`, `clearFailed`, `transactFailed`, `queryFailed`) and semantic ones (`ItemAlreadyExists`, `ConditionFailed`, `NoItemToUpdate`, `NoItemToDelete`, `NoItemToRestore`). A direct duplicate insert consistently returns `ItemAlreadyExists`; an optimistic or transaction conflict returns `ConditionFailed`.

## When to reach for which

Not a rivalry — a placement decision per tier, over one codebase:

| Situation                                      | Reach for                                                                                                   |
| ---------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Client-side store in a web app                 | idb — a real, indexed, transactional database on the user's machine                                         |
| Offline-first / local-first UI                 | idb behind [tanstack-sync](/docs/std-toolkit/tanstack-sync) — writes survive offline, sync when reconnected |
| Unit and integration tests                     | SQLite, `:memory:` — real SQL, zero infrastructure                                                          |
| Per-partition data at the edge                 | SQLite in a Durable Object — one database per channel                                                       |
| Shared multi-tenant store at scale             | DynamoDB — horizontal scale and managed durability                                                          |
| Server-side conditional writes, no transaction | DynamoDB — condition and update expressions                                                                 |

And the reason this table can exist at all: the layer above doesn't care. The [sync engine](/docs/std-toolkit/tanstack-sync) asks one question — sorted items after a cursor — and every adapter answers it identically. Keep idb on the client, a server adapter in the cloud, and change nothing about how your entities are defined in between.
