You know the storage model by now: one table, entity services, item collections, range queries over a sort key. You learned it in [DynamoDB's vocabulary](/docs/std-toolkit/database-adapters), and DynamoDB is where it was born.

But think about where your chat app's code actually runs. Unit tests, where spinning up DynamoDB Local for every suite is a tax you pay forever. Local dev, where you want a database that's a file you can delete. A Cloudflare Durable Object, where DynamoDB isn't even an option. The usual answers are bad in different ways: mock the data layer and your tests stop testing the data layer, or write a second data layer for the second database and watch the two drift apart one bugfix at a time.

std-toolkit's answer is to make the _model_ portable instead. The `std-toolkit/sqlite` subpath is the same single-table topology — same builders, same key derivation, same [entity envelope](/docs/std-toolkit/core) — implemented over SQLite. Your app code doesn't change; the physics underneath it does. And because SQLite runs anywhere a file (or a Durable Object) does, the "database-agnostic" claim stops being a slogan and becomes something you can verify in a test suite.

This page walks the chat app onto SQLite, top to bottom. Everything semantic — what `insert` returns, how keys derive, how queries paginate — is the [shared model](/docs/std-toolkit/database-adapters) and holds here verbatim; what follows is the SQLite-flavored surface.

## The table: `SQLiteTable`

```ts title="table.ts"
import { SQLiteTable } from 'std-toolkit/sqlite';

export const table = SQLiteTable.make('chat_data')
  .primary('pk', 'sk')
  .index('IDX1', 'IDX1PK', 'IDX1SK')
  .build();
```

Same builder shape as the DynamoDB adapter: a physical table name, a primary key pair, and generic secondary index slots. The connection stays in the runtime layer (next page), so several table definitions can share one database.

Physically, `setup()` (below) turns this into one SQLite table: `pk` and `sk` as a composite primary key, a `_data` column holding the encoded entity as JSON, the meta columns `_e`, `_v`, `_u`, `_d` from the [envelope](/docs/std-toolkit/core/meta), and a nullable column pair per index slot. All rows sharing a `pk` value, ordered by `sk`, form an item collection — the exact structure the whole toolkit is built on, now answered by a `WHERE pk = ? AND sk > ? ORDER BY sk` that SQLite serves off its primary index.

## Entities: `SQLiteEntity`

```ts title="entities.ts"
import { Channel, Message } from './schemas.js';
import { table } from './table.js';

export const messages = table
  .entity(Message)
  .primary({ pk: ['channelId'] })
  .index('IDX1', 'byAuthor', { pk: ['authorId'] })
  .build();

export const channels = table.entity(Channel).primary().build();
```

Read it the way you read the DynamoDB version, because it _is_ the DynamoDB version: messages are partitioned by channel (`pk` derives to `Message#C-general`, `sk` is the message's ULID id), and channels — `primary()` with no fields — all live in one collection under `pk = "Channel"`. The `byAuthor` index maps onto the table's `IDX1` slot with `_u` as its default sort key; the [indexes page](/docs/std-toolkit/sqlite/indexes) unpacks that machinery.

The service surface is the shared one: `insert` refuses to overwrite, `getAndUpdate` re-stamps `_u`, `delete` writes a tombstone, `restore` lifts it, `query` slices an item collection with a range operator, and `queryStream` walks a whole collection as a `Stream` of batches. One round trip to make it concrete:

```ts
import { Effect } from 'effect';
import { nextUlid } from 'std-toolkit/core';

const program = Effect.gen(function* () {
  const sent = yield* messages.insert({
    messageId: yield* nextUlid,
    channelId: 'C-general',
    authorId: 'U-ada',
    body: 'works on SQLite too',
  });

  const { items: latest } = yield* messages.query(
    'primary',
    { pk: { channelId: 'C-general' }, sk: { '<': null } },
    { limit: 50 },
  );
});
```

If this looks like the code from the shared-model page with nothing changed — that's the point. Reads still fold old rows forward through the eschema's migrations; a v1 message stored last year decodes to the current shape here just as it would on DynamoDB.

## Singletons: `SQLiteSingleEntity`

Some state has a name but no id — there's exactly one of it. `SQLiteSingleEntity` stores one row per database, keyed by the entity's name alone:

```ts title="settings.ts"
import { WorkspaceSettings } from './schemas.js';
import { table } from './table.js';

export const settings = table
  .singleEntity(WorkspaceSettings)
  .default({ maintenanceMode: false, motd: null });
```

Two things are different from a keyed entity, both deliberate. First, the builder ends at `.default(...)` — no `.build()` — because the default value _is_ the last required piece: `get()` never returns null, it returns the default (with a synthetic empty `_u`) until something has been written. Second, the surface is just `get`, `put`, `getAndUpdate`, and `reset` — no delete, no query, no tombstones, because "one row that always exists" has no use for any of them. `put` upserts unconditionally; `getAndUpdate` merges a partial into the current value — the schema default when nothing is stored yet — and writes it back guarded on the `_u` it read; `reset` writes the default value back. Single entities are never deleted.

One row _per database_ is a real constraint to notice — and in the Durable Object deployment on the [next page](/docs/std-toolkit/sqlite/runtimes), where each channel gets its own database, it quietly becomes "one per channel", which is usually what you wanted anyway.

When a repository boundary needs an explicit return type, the SQLite barrel exports both envelope shapes:

```ts
import type { EntityType, SingleEntityType } from 'std-toolkit/sqlite';
import type { ESchemaType } from 'std-toolkit/eschema';

type MessageValue = ESchemaType<typeof Message>;
type SettingsValue = ESchemaType<typeof WorkspaceSettings>;

export type StoredMessage = EntityType<MessageValue>;
export type StoredSettings = SingleEntityType<SettingsValue>;
```

`EntityType<T>` is the keyed `{ value, meta }` result with `_e`, `_v`, `_u`, and `_d`; `SingleEntityType<T>` is the singleton result without tombstone metadata. Calls on `SQLiteEntity` and `SQLiteSingleEntity` infer these automatically, so name them only when the envelope itself crosses one of your module boundaries.

## Provisioning and batches: `setup` and `transact`

There's no separate registry object and no name-based lookup — the table coordinates the concerns that span every entity sharing it, and you keep the references that `.build()` handed you. Two table members deserve more than a sentence.

**`setup()` provisions at runtime.** On DynamoDB, creating the table is a deploy-time step outside your program. On SQLite the database is a file you already own, so the toolkit just does it:

```ts
yield * table.setup();
```

This creates the table with all meta and index columns, adds any index columns missing from an existing table, and creates the SQL indexes — every step a no-op if it already happened. Idempotent setup on boot is what makes "fresh in-memory database per test" a three-line fixture instead of an infrastructure project.

**`transact(ops)` commits a batch atomically.** Each entity builds write descriptions ahead of time — `insertOp`, `getAndUpdateOp`, `deleteOp`, `restoreOp` — and `table.transact(ops)` applies the whole batch inside one `BEGIN … COMMIT`, all-or-none:

```ts
yield *
  table.transact([
    yield *
      channels.insertOp({
        channelId: 'C-standup',
        name: 'standup',
        topic: 'daily sync',
      }),
    yield *
      messages.insertOp({
        messageId: yield * nextUlid,
        channelId: 'C-standup',
        authorId: 'U-ada',
        body: 'welcome to #standup',
      }),
  ]);
```

Either the channel and its first message both exist, or neither does — any op whose condition fails (an `insertOp` onto an existing row, or a guarded `getAndUpdateOp` whose `_u` moved) rolls the whole batch back with `ConditionFailed`. The batch is write-only: a list of pre-built ops, not code that reads and branches mid-transaction. Broadcasts are buffered and only emitted after commit — subscribers never observe a write that later rolled back. How this compares to DynamoDB's `transact` is on the [differences page](/docs/std-toolkit/sqlite/differences-from-dynamodb).

## The seam underneath: `SQLiteDatabase` and `SQLiteError`

You may have noticed nothing above opened a database connection. Every operation requires `SQLiteDatabase`, the narrow SQL service all of this compiles down to, and fails with `SQLiteError` variants such as `ItemAlreadyExists`, `NoItemToUpdate`, and `CreateTableFailed`. Providing the runtime through better-sqlite3, Node's built-in driver, Bun, or a Durable Object is a one-line layer, and it is the whole subject of the next page.
