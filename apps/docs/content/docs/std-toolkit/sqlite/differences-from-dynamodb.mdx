title: Differences from DynamoDB
description: The honest diff between the two adapters — consistency, setup, query surface, writes, transactions, deletes — and when to reach for which.
---

Three pages of "it's the same model" should have raised your skeptic's eyebrow. Two databases with this little in common — a managed, distributed key-value store and an embedded SQL file — cannot be _identical_ behind one API, and a toolkit that claimed they were would be hiding something. So here is the full diff, verified against the adapters' source, organized by what you'd actually hit. The summary up front: the shared contract — entity services, key derivation, envelopes, range queries, sk-as-cursor pagination, tombstone deletes — genuinely is identical. The differences live at the edges, and each one is a database being honest about its own physics.

## Consistency

**SQLite: everything is strongly consistent.** One database, one writer at a time — every read observes every prior write, through the primary key and through every [secondary index](/docs/std-toolkit/sqlite/indexes). There is no consistency knob because there is nothing to configure.

**DynamoDB: consistency is a spectrum you manage.** Reads are eventually consistent by default; the adapter exposes `ConsistentRead` on `get` to opt into strong reads where DynamoDB allows them. GSI queries are always eventually consistent — no opt-out exists.

This is the difference you'll feel first, because it shows up in tests: assertions that need retry-until-visible against DynamoDB pass immediately against SQLite. Which is precisely why testing on SQLite and deploying on DynamoDB requires a moment of honesty — don't let strong-consistency habits leak into code that will run against GSIs. Write code that tolerates the eventual case, and SQLite simply never exercises the tolerance.

## Setup and provisioning

**SQLite provisions itself at runtime.** `table.setup()` is idempotent DDL — create the table, add missing index columns, create indexes — safe to run on every boot. New index slot? Re-run setup, even against a table with data.

**DynamoDB provisions out-of-band.** The table builder hands you `createTableDefinition()` — the attribute definitions and GSI declarations — and creating or altering the table is a deploy step through IaC or the AWS API, on AWS's timeline (GSI backfills can take a while on large tables).

## Query surface

Small, honest deltas in what a query can say:

- **Sort-key operators.** Both entity layers take `<`, `<=`, `>`, `>=` with a nullable cursor, plus `beginsWith` for prefix queries.
- **Default page size.** Pass no `limit` and SQLite returns up to 100 rows. DynamoDB reads until your `limit` or its 1 MB page cap, whichever bites first.
- **Page truncation.** DynamoDB can cut a page short at 1 MB and hands back a `LastEvaluatedKey`; SQLite never truncates — a page is exactly what you asked for. You'll rarely notice either way, because the shared pagination idiom doesn't use `LastEvaluatedKey`: the last item's sort key is the next cursor, and that loop runs identically on both engines.

## Writes: expressions vs read-merge-write

A real API divergence. DynamoDB leans on _server-side_ expressions, and the adapter surfaces them: `update` there accepts either a plain partial or an expression-builder callback (`set`, `opAdd`, …), plus an optional condition expression that makes the write atomic-or-rejected at the database (the [expressions page](/docs/std-toolkit/dynamodb/expressions) covers this machinery).

SQLite has no expression-based `update`. Its portable read-modify-write is `getAndUpdate`, which takes a plain partial (or a `current => partial` callback):

```ts
yield *
  messages.getAndUpdate(
    { channelId: 'C-general', messageId },
    { body: 'edited on sqlite' },
  );
```

Under the hood it reads the row, merges, re-encodes, and writes back guarded on the `_u` it read — retrying on a concurrent-write conflict. No expression builders, no condition parameter. `getAndUpdate` exists on the DynamoDB adapter too, so read-merge-write code ports verbatim; SQLite simply has no server-side expression form to reach past it.

One write guarantee is carefully kept identical: **insert refuses to overwrite** on both engines. DynamoDB enforces it with an `attribute_not_exists` condition; SQLite enforces it with the primary-key constraint. Both surface it as the same `ItemAlreadyExists` failure.

## Transactions: the same shape

Both adapters expose exactly one transaction primitive, and it's the same one: `table.transact(ops)`, a write-only batch that commits all-or-none.

**Declare the writes, then commit — on both engines.** Entities build operation descriptions ahead of time (`insertOp`, `getAndUpdateOp`, `deleteOp`, `restoreOp`), and `table.transact(ops)` submits the batch atomically:

```ts
yield *
  table.transact([
    yield *
      channels.insertOp({
        channelId: 'C-standup',
        name: 'standup',
        topic: 'daily sync',
      }),
    yield *
      messages.insertOp({
        messageId: yield * nextUlid,
        channelId: 'C-standup',
        authorId: 'U-ada',
        body: 'kicking off',
      }),
  ]);
```

The batch is data, not code: you cannot read, branch, or compute inside it. When a write must depend on the current value, build the decision _before_ the batch — `getAndUpdateOp` pre-reads the row and embeds an optimistic `_u` guard, so a concurrent change surfaces as the transaction's `ConditionFailed` and rolls everything back. For a single guarded read-modify-write outside a batch, `getAndUpdate` is the portable one-call form. [Broadcasts](/docs/std-toolkit/core) from a committed batch fire in op order; a failed one broadcasts nothing.

SQLite once offered an interactive `transaction(effect)` that ran arbitrary reads and writes inside `BEGIN … COMMIT`; that has been retired. The write-only `transact` batch is now the only transaction vocabulary on both engines, which is exactly why this row of the diff is empty.

## Deletes and destructive escape hatches

`delete` is a tombstone on both engines — `_d` flips, `_u` re-stamps, the row stays for sync consumers. The destructive escape hatches now have the same shape on every adapter:

- **`entity.hardDelete(key, 'I KNOW WHAT I AM DOING')`** physically removes one item.
- **`dangerouslyRemoveAllItems('I KNOW WHAT I AM DOING')`** removes every item in its scope: the whole physical table when called on a table, or only that entity's rows when called on an entity.

The warning is identical on both: hard deletion erases the tombstone, so anything syncing from the table will never learn the row died. Reach for it in tests and cleanup jobs, nowhere near synced data.

## Errors

Same ergonomics, different vocabularies: every SQLite operation fails with `SQLiteError`, every DynamoDB operation with `DynamoDBError` — tagged variants you handle with ordinary Effect combinators. The variant sets reflect their engines (SQLite has `CreateIndexFailed`; DynamoDB has expression and transact failures), while shared semantic variants such as `ConditionFailed`, `ItemAlreadyExists`, `NoItemToUpdate`, and `NoItemToDelete` use the same tags on both.

## When to reach for which

Not a rivalry — a deployment decision per environment, over one codebase:

| Situation                                             | Reach for                                                                                                                 |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| Unit and integration tests                            | SQLite, `:memory:`, per-test databases — real SQL, zero infrastructure, no eventual-consistency flake                     |
| Local development                                     | SQLite — the database is a file you can inspect and delete                                                                |
| Per-partition data at the edge                        | SQLite in a Durable Object — [one database per channel](/docs/std-toolkit/sqlite/runtimes) is the topology's natural home |
| Single-server apps, embedded, small deployments       | SQLite — transactions and strong consistency with no managed service                                                      |
| Shared multi-tenant store at scale, serverless fleets | DynamoDB — horizontal scale and managed durability are what you're paying for                                             |
| Server-side conditional writes without a transaction  | DynamoDB — condition and update expressions                                                                               |

And the reason this table can exist at all: the layer above doesn't care. The [sync engine](/docs/std-toolkit/tanstack-sync) asks one question — sorted items after a cursor — and both adapters answer it identically. Test the whole sync path against SQLite in CI, run DynamoDB in production, and change nothing in between.
