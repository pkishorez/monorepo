You know the [shared storage model](/docs/std-toolkit/database-adapters): one table, entity services built from eschemas, keys derived from fields. What's left is making it talk to an actual DynamoDB — and this is where most DynamoDB codebases get messy. The official client stack is enormous, connection config leaks into every module that touches data, and the table name gets baked into definitions so deeply that pointing the same code at a local instance for tests becomes a project.

The adapter splits the problem into two halves that never touch: your **table and entities are reusable topology** — a logical identity, but no physical table name, region, or credentials — and an **Effect Layer binds that topology to physical tables** at the edge of your program. Swap the layer, and identical code runs against production, staging, a local container, or a test table.

## The table is pure topology

`DynamoTable` gives the topology a logical identity and describes its key structure — which attributes are the primary partition and sort key, and which secondary indexes exist:

```ts title="table.ts"
import { DynamoTable } from 'std-toolkit/dynamodb';

export const table = DynamoTable.make('chat')
  .primary('pk', 'sk')
  .gsi('GSI1', 'GSI1PK', 'GSI1SK')
  .build();
```

The attribute names are deliberately generic. In single-table design the physical attributes carry no domain meaning — `pk` holds `Message#C-general` in one row and `Channel` in another — so naming them `pk` and `sk` is honest. The `.gsi(...)` call declares a physical global secondary index we'll put to work on the [indexes page](/docs/std-toolkit/dynamodb/indexes); ignore it for now.

The `'chat'` argument is a logical identity used to bind this table at runtime. It is not an AWS table name: production, staging, and tests can bind the same definition to different physical tables.

## Entities: the chat app's schemas, bound to the table

The entity services work exactly as taught in [Database adapters](/docs/std-toolkit/database-adapters) — here's the chat app's full set, built from the [eschemas](/docs/std-toolkit/eschema) you've seen throughout these docs:

```ts title="entities.ts"
import { table } from './table';
import { Message, Channel, WorkspaceSettings } from './schemas';

export const messages = table
  .entity(Message)
  .primary({ pk: ['channelId'] })
  .build();

export const channels = table.entity(Channel).primary().build();

export const settings = table
  .singleEntity(WorkspaceSettings)
  .default({ allowGuestAccess: false, defaultChannelId: 'C-general' });
```

`messages` partitions by channel — one channel, one item collection. `channels` declares no pk fields, so its partition key is just the entity name `Channel`: every channel in the workspace lives in a single item collection, sorted by `channelId`.

`table.singleEntity(...)` is the singleton storage binding for things that exist exactly once — workspace settings, feature flags, counters. It accepts an ordinary `ESchema` and requires a **default value**, which buys you a guarantee the keyed entities can't offer: `get` never returns null.

```ts
const current = yield * settings.get();
// always a value — the default (with synthetic meta) if nothing is stored yet

yield * settings.put({ allowGuestAccess: true, defaultChannelId: 'C-general' });
yield * settings.update({ update: { allowGuestAccess: false } });
```

Its surface is deliberately smaller than a keyed entity: `put` is an unconditional upsert, `update` fails with `NoItemToUpdate` if nothing was ever written, and `reset` writes the default value back as a real record — single entities are never deleted, so `get` and any broadcast agree on the same `_u`. There's no soft-delete tombstone (`_d`) here — a singleton isn't part of any synced item collection, so nothing downstream needs to observe a deletion.

The adapter also exports the result shapes as `EntityType<T>` and `SingleEntityType<T>`. You rarely annotate a direct call because TypeScript infers it, but they are useful at a boundary you own — for example, the return type of the chat app's repository:

```ts
import type { EntityType, SingleEntityType } from 'std-toolkit/dynamodb';
import type { ESchemaType } from 'std-toolkit/eschema';

type MessageValue = ESchemaType<typeof Message>;
type SettingsValue = ESchemaType<typeof WorkspaceSettings>;

export type StoredMessage = EntityType<MessageValue>;
export type StoredSettings = SingleEntityType<SettingsValue>;
```

Both are `{ value, meta }` envelopes. `EntityType` carries keyed-entity meta (`_e`, `_v`, `_u`, `_d`); `SingleEntityType` carries the singleton subset (`_e`, `_v`, `_u`). These are the DynamoDB adapter's concrete read shapes, while the similarly named core exports describe the cross-toolkit envelope contract.

## `DynamoDB.client` and `DynamoDB.layer`

Everything above is inert until something provides the `DynamoDB` service. The service resolves each logical table to an authenticated client and physical table name, so one Effect runtime can use several tables, accounts, regions, or DynamoDB-compatible endpoints.

Create a table-independent client, then bind the table definition to it:

```ts title="dynamo-live.ts"
import { DynamoDB } from 'std-toolkit/dynamodb';
import { table } from './table';

const client = DynamoDB.client({
  region: 'eu-west-1',
  credentials: {
    accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
    secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
    // sessionToken: '...' — optional, for temporary credentials
  },
});

export const liveLayer = DynamoDB.layer({
  table,
  client,
  tableName: 'chat-app-prod',
});
```

`DynamoDB.client` accepts static credentials or synchronous/asynchronous credential providers, plus an optional region and endpoint. The endpoint is how local development works:

```ts title="dynamo-local.ts"
import { DynamoDB } from 'std-toolkit/dynamodb';
import { table } from './table';

const localClient = DynamoDB.client({
  region: 'us-east-1',
  credentials: { accessKeyId: 'local', secretAccessKey: 'local' },
  endpoint: 'http://localhost:8090',
});

export const localLayer = DynamoDB.layer({
  table,
  client: localClient,
  tableName: 'chat-app-local',
});
```

Now run a program by providing whichever layer fits the environment:

```ts title="main.ts"
import { Effect } from 'effect';
import { nextUlid } from 'std-toolkit/core';
import { messages } from './entities';
import { liveLayer } from './dynamo-live';

const program = Effect.gen(function* () {
  const sent = yield* messages.insert({
    messageId: yield* nextUlid,
    channelId: 'C-general',
    authorId: 'U-ada',
    body: 'we are live',
    reactions: {},
  });
  return sent;
});

await Effect.runPromise(program.pipe(Effect.provide(liveLayer)));
```

The table definition owns a stable logical identity and reusable topology. The layer owns deployment-specific bindings: physical table names and clients. Your production table, staging table, and throwaway test table can therefore share one definition.

## The client underneath

`DynamoDB.client(config)` returns the lowest layer of the adapter: a complete, Smithy-typed `DynamoDBClient` whose methods (`getItem`, `putItem`, `query`, `transactWriteItems`, `createTable`, ...) are Effect-wrapped calls to DynamoDB's HTTP API, signed by [aws4fetch](https://github.com/mhart/aws4fetch). No AWS SDK runtime is required.

Day to day the entity services are the API. You will meet the client in table administration, because provisioning sits outside a runtime binding. Pair it with `table.createTableDefinition()`, which turns your topology into a ready-made `CreateTable` input without a physical `TableName`:

```ts title="provision.ts"
import { Effect } from 'effect';
import { DynamoDB } from 'std-toolkit/dynamodb';
import { table } from './table';

const client = DynamoDB.client({
  region: 'us-east-1',
  credentials: { accessKeyId: 'local', secretAccessKey: 'local' },
  endpoint: 'http://localhost:8090',
});

await Effect.runPromise(
  client.createTable({
    TableName: 'chat-app-local',
    ...table.createTableDefinition(),
  }),
);
```

That's the whole local-dev bootstrap: one script creates a table whose shape is guaranteed to match your code, because it _is_ your code.

Client calls return generated AWS response and error types directly. Table and entity operations resolve their binding from `DynamoDB` and map failures to the adapter's direct `DynamoDBError` variants.

That's the full wiring: reusable topology in code, deployment bindings in a layer, and provisioning from the same definition. Next: the part of the adapter that earns its keep on every write — secondary indexes as typed derivations.
