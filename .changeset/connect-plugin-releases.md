Every Plugin runs at a Release Cloud Connect names, and Code calls it at the Release it was built with (ADR 0006).

**BREAKING**: ke-connect, Cloud Connect and Code must all be on this release together. This is a fresh start: none of them reads what an earlier one sends or stores. Older ke-connects must `npm i -g @kestack/connect@latest`.

- Every wire value (`Connection`, `ConnectionReport`, `ConnectionStatus`, `HarnessAccountInfo` and the rest) is at its first version. `Connection` has `minConnect`, the Minimum Connect: the oldest `ke-connect` let run the Plugins, null when Cloud Connect names none. `latestVersion` is gone; Code asks to update `ke-connect` only when a Connection is Outdated (`isOutdated`), below the Minimum Connect. `HarnessAccountInfo.resolvedConfigFolder` is never null.
- Cloud Connect keeps its Connections in a new D1 database, `cloud-connect-<stage>`, replacing `connect-<stage>`, which the deploy deletes: every Connection reports itself again on its next Heartbeat. Its records start at their first version.
- The code Plugin's records (Projects, Sessions, Harness Accounts) start at their first version, so a `code.db` from an earlier release does not open: delete it from the Connection's data folder.
- Cloud Connect decides the latest Release of each Plugin from its Release Log, `src/plugins/<name>/releases.json`; `pnpm release:plugin code "<what changed>"` builds the Plugin and appends its hash. A deployed Stage refuses a build that is not the latest Release, and puts it on the R2 Shelf; `alchemy dev` on a folder Shelf, as a `file:` URL. `serve` and `serveOver` from `./worker` take `minConnect`, and the Worker reads `MIN_CONNECT`; `minConnect` in `package.json` is the Minimum Connect, `0.0.4`.
- A Connection serves a Plugin only at `/<plugin>/<sha256>/rpc`, while it runs that Release; anything else is 404. A WebSocket for another Release is accepted and closed at once with 4409, `PLUGIN_MISMATCH`, its reason `{"running": <hash or null>}`; any other request answers 409 with the same JSON. `--plugin <name>=<file>` is gone: development runs the Plugin from the folder Shelf, as a deployed Connection does, after `pnpm build:plugin`.
- A Connection below the Minimum Connect reports once, then stops, and `serve` fails with what to do: `npm i -g @kestack/connect@latest`. It keeps the Release of each Plugin it last wanted in `wanted.json`, and starts its Plugins at them while Cloud Connect cannot be reached; Cloud Connect's answer wins.
- `ke-connect serve` runs the Connection as two parts that never see each other: `actor-online`, the tunnel and the Heartbeat, and `actor-plugins`, the router and the Plugins. Who the Connection is (its folders, `connection.json` and Sign-in) is in `identity/`. It no longer warns about folders an earlier ke-connect left.
- Cloud Connect has a door of its own, `@kestack/connect/cloud`: `CloudClient`, `VersionGap`, `Connection`, `ConnectionStatus`, `addressOf`, `authInfo`, `isOutdated`, `pluginPath`, `PLUGIN_MISMATCH`, `PluginMismatch` and `mismatchOf` come from there, and `@kestack/connect/code` no longer exports them, nor `CloudApi`, `ConnectionReport`, `TunnelCheck`, `ConnectionForgotten`, `ConnectionTaken`, `RPC_PATH` or `AUTH_PATH`. The code Plugin's own files are under `src/plugins/code/serve/`, and it no longer bundles the Cloud client.
- Code is built with the latest Release in the code Plugin's Release Log as `import.meta.env.PLUGIN_CODE`, and its build fails without one; under `pnpm dev`, with the sha256 of Connect's `dist/plugin/code.mjs`. Each socket dials `<tunnel>/code/<sha256>/rpc`. A Connection that closes it with `PLUGIN_MISMATCH` is Updating while Cloud Connect wants Code's Release, or none ("Updating Connect…"); otherwise Code is Stale and moves to its newest build ("Updating Code…"). `CodeClients.make` hands `open` a `SocketWatch` for each Connection's sockets; `CodeClients.mismatch(id)` says which Release a Connection said it runs.
- `@kestack/cli-platform`: `Downloads.fetch` copies a `file:` URL into the cache and checks its hash, as it does a download; one naming no file fails with `DownloadFailed` and `missing: true`, which `ActorPlugin` reports as `<name> <hash> isn't on the shelf; run the build`.
- `@kestack/cli-platform`: `ActorPlugin` starts a new Release's process only once the old process has exited, its finalizers done or it killed after its grace, not only once it left the socket, so two never run at once on one Plugin's folders.
- `@kestack/cli-platform`: every `single` claim holds a lock while it listens, letting it go before its handlers are built, and while it takes over a socket file a dead process left behind: the same kind of port lock the download cache uses. Of many processes claiming at once, exactly one is `Acquired` and the rest are `AlreadyRunning`, so two Connections never run under one name.
- `ke-connect serve` keeps what Cloud Connect's `/auth` said in `auth.json`, beside the Sign-in. A Connection that signed in before starts while Cloud Connect cannot be reached, or does not answer `/auth` in five seconds: it signs in as last time with the Sign-in kept, checking it with the Auth Worker for five seconds at most, runs its Plugins at the Releases in `wanted.json`, and keeps sending its Heartbeat until Cloud Connect answers; a Report not answered in ten seconds is Unsent. `authInfo` aborts its fetch when interrupted. Signing in again, once Cloud Connect refuses the Sign-in, asks `/auth` first and signs in through the Auth Worker it names then, keeping it in `auth.json`; its one Device, and the checks of calls Cloud Connect refuses, follow that Auth Worker from then on. Revoking the old Sign-in has five seconds, and it is forgotten either way. A first Sign-in still needs Cloud Connect.
- A personal Stage, `alchemy deploy --stage <name>`, refuses to deploy, saying it has no URL: its Worker has no domain, so no Connection could read its Shelf, and it would have named no Plugin. Deploy `prod`, `demo` or `prN`, or run `alchemy dev`.
- `@kestack/auth-toolkit`: `device`'s `url` may be an Effect, read at each call to the Auth Worker, so a Device follows an Auth Worker that moves. A refused call fails at once, its check running beside it for five seconds at most; a sign-out, finding the Auth Worker included, has five seconds, and forgets the token either way. A sign-in begun at an Auth Worker the Device has moved from fails `DeviceLoginFailed`, `reason: 'moved'`, and keeps nothing.
