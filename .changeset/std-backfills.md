Setup reindexes by itself. When an index or access pattern changes on a persistent table, or a schema an indexed entity reaches gains a version, setup applies the topology, scans the table with strongly consistent reads, rewrites each row whose index keys drifted (`drift`, `reindex`), and only then records the Stored contract. It keeps no progress: a setup that stops part-way leaves the old contract, and the next one reindexes again. A row an app write moves meanwhile is read again and retried up to three times. `SetupOutcome` `applied` lists the entities it `reindexed`, and a row it cannot rewrite fails setup with `DatabaseError`. `@kestack/std-toolkit/db/dynamodb` exports `DynamoDB.setup`. See `docs/evolving-schema.md`.

- Breaking: a table is one declaration. Declare each entity on it before `build`, as `.entity(Task, (e) => e.primary({ pk: ['boardId'] }))` and `.singleEntity(Settings, { default })`, and use it as `table.Task`. `table.entity(Task)…build()` and `table.singleEntity(Settings).default(…)` are gone.
- Breaking: `expectTableShippable` comes from `@kestack/std-toolkit/db/testing`. `@kestack/std-toolkit/snapshot/vitest` exports only the file check, `expectSnapshotFile`.
- Breaking: the Stored contract is kept as rows inside the table on every adapter, and an old `_std_contract` is not converted. A table holding rows but no contract is refused if persistent and wiped if disposable; give a persistent table a new physical table name.
- Breaking: an index change no longer passes a persistent table with a warning: setup reindexes it. A disposable table is wiped instead. The snapshot impact `requires-backfill` is renamed `requires-reindex`. IndexedDB's `onBackfill` is removed, and `setUpFromSnapshot` is gone from `@kestack/std-toolkit/db/sqlite`.
- Breaking: a breaking change on a persistent table is still refused; the way past is a new physical table and a table migration into it, coming as `StdTable.migrate`.
- Breaking: `DynamoDB.table` in `@kestack/std-toolkit/alchemy` is its own resource that creates the table and runs setup at deploy, reindex included. It takes `region`, and `credentials` or the `AWS_*` variables, and an optional `endpoint`; removing it leaves the table. `D1.table` and `DynamoDB.table` no longer add a deploy guard; `DeployGuard.table` is for an IndexedDB or Durable Object table, and fails the deploy where setup would refuse.
