# Add scan, drift, and reindex to StdTable for index backfill

std-toolkit had no way to act on a `requires-backfill` snapshot change. Schema-shape drift already self-heals through eschema's lazy read migration, but a secondary-index or derivation change leaves existing rows unqueryable on the new access pattern until something recomputes and rewrites their derived keys — and nothing in the toolkit did that. `StdTable` gains three composable primitives instead of one automated `migrate()` call: `scan()` walks the table and returns raw `EncodedItem`s; `drift(item)` dispatches by the item's `_e` against the table's own entity registry, recomputes the item's derived keys under the current registration, and reports whether its secondary-index keys differ from what is stored (ignoring `_v`/payload-only differences, since those never affect queryability); `reindex(currentForm)` writes the corrected item back. A primary partition-key or sort-key difference is not repairable Drift: `drift` fails with `PrimaryKeyDrift`, because moving an Entity to a new identity must be an explicit delete followed by an insert. All three operations live on `StdTable` itself, not on the Entity surface and not in a new bounded context, because the table alone holds the full entity registry `drift` needs to dispatch on `_e`, and once `drift` has produced a `currentForm`, writing it back needs no entity-specific schema knowledge — just a keyed conditional put.

`reindex` deliberately does not mint a new `_u` or fire a Change Notice: it writes `currentForm` guarded on and preserving the exact `_u` it carries, an unconditional-write path that bypasses the normal Entity-surface write-and-broadcast machinery. Building `currentForm` decodes and then encodes the item. When the stored payload is old, this can persist the latest equivalent encoded payload and `_v` together with the corrected secondary-index keys. This is safe because sync's Convergence Rule only cares about `_u` recency, and the latest decoded domain value did not change — only the row's physical representation changed. A row a real write touches in the meantime already gets its keys re-derived for free, since `encode` always re-derives from the current registration; `reindex` exists only for rows nothing else would otherwise rewrite. A conflict (the row's real `_u` moved since it was read) fails with a distinct `ReindexConflict` reason rather than reusing `ConditionFailed`, and the primitive does not retry internally — the caller composes retry or skip.

Topology-level diffing (`safe` / `breaking` / `requires-backfill`) is unchanged: it still runs entirely through `table.snapshot()` and `Snapshot.diff()`, composed by whatever calls them. `db` takes on no new dependency on `snapshot`'s comparison logic. Primary-key and entity-identity changes remain `breaking` and human-led — only secondary-index and derivation drift is addressed here.

## Considered Options

- **One automated `migrate()` that scans, diffs, and rewrites in a single call** — rejected. Detection and remediation are different concerns with different blast radii; collapsing them removes the caller's ability to inspect what would change, or to skip rows deliberately, before committing a rewrite.
- **`getAndUpdate` as the write-back path** — rejected. It always mints a new `_u` and always broadcasts a Change Notice, which would flood subscribers with notices for rows whose domain value never changed — this is exactly the noise `reindex` exists to avoid.
- **A migration-state record (a SingleEntity per table) tracking the last-reconciled topology** — considered as a fast-path to skip scanning when nothing changed, but demoted to optional future bookkeeping for a not-yet-designed migration-helper module. The core primitives work with zero stored state.
