# The per-table test file replaces the CLI and pins migrations with golden rows

The `std-toolkit snapshot` CLI, its `std-toolkit.snapshot.ts` entry convention, its file-based baseline, and the Jiti dependency are removed. This supersedes ADR 0003. In their place `std-toolkit/snapshot/vitest` offers one call per table, `expectTableSnapshot(table, file)`, which wraps a Vitest file snapshot of a `TableSnapshotFile` document: the table's schema contract plus **golden rows** for every migration step of every ESchema the table reaches, nested ones included. On a mismatch the failure message is the classified change list, so a reviewer or an agent reads "Task v1 edited" or "Migration Task → v2" rather than a JSON diff. `vitest -u` accepts the current document, exactly as it does for any file snapshot.

Two baselines with different approval semantics were the source of a real gap: the CLI accepted a breaking change on approval, so the first refusal happened at deploy. One committed file per table, produced by the same test runner every project already has, keeps the review where the code review is. The failure message is the part that matters; the file format is not something a person reads.

A golden row is one generated value of a version together with what the next version's migration turns it into, both in their persisted encoded form. Twenty are drawn per step from the previous version's schema with a fixed seed. Rows are per step, never whole chain, so appending a version adds rows and touches no existing ones, and a rewritten or impure migration changes a stored output and classifies as `breaking`. Once a step's rows are in the file, capture replays the stored inputs through the current migration instead of drawing again, so a change in the generator can never look like a rewritten migration. Authors never write rows by hand. Rows live only in the test file: the table's enforcement baseline holds the schema contract alone, so a deploy catches a changed shape and CI catches a rewritten step.

Every snapshot document is now an ESchema of its own (`TableSnapshot`, `ESchemaSnapshot`, `TableSnapshotFile`, and db's `TableBaseline`), all starting at `v1` with no migration from the earlier formats. A document written by an older toolkit reads forward through a normal migration instead of becoming unreadable, which is the only design where a library upgrade cannot strand a live table. Effect's `Schema.Json` is a declaration the ESchema field policy refuses, so the documents use a structural JSON schema instead. A nested ESchema's composition now declares its persisted form, fields plus version stamp, on its encoded side and supplies an arbitrary for it, so generated rows hold real nested values.

Rejected: hashing migration source text, because formatters and minifiers change it; author-supplied samples on `evolve`, because Effect already generates values from a schema and a required literal per step is friction for no gain; a rendered text file beside the JSON, because the failure message already carries the readable form; and keeping golden rows in the table baseline, because the deploy check protects data, the test protects code, and the baseline item should stay small and schema-only.
