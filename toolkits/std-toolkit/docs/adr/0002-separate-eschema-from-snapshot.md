# Snapshot depends on ESchema through introspection

ESchema owns schema construction, evolution, migration, encoding, decoding, composition, and a package-private read-only introspection contract. Snapshot consumes that contract to capture semantic documents; ESchema never imports snapshot. Standalone capture therefore uses `Snapshot.capture(eschema)` instead of `eschema.snapshot()`, while database tables retain `table.snapshot()` because the adapters already depend on snapshot.

Both contexts use capability-focused deep modules over shared domain modules. The three ESchema variants compose common object-schema behavior instead of sharing a class hierarchy or universal builder, and each variant owns its small fluent builder. Valid instances can only be created through the fluent `make`/`evolve`/`build` path; raw constructors are not public construction APIs. Snapshot keeps one public `Snapshot` facade while capture, decoding, validation, diffing, inspection, and rendering remain independent modules. Database entity registration belongs to the shared database context, which passes plain table source data to snapshot's table-capture boundary.

This direction prevents the former ESchema↔snapshot cycle and makes the layer graph enforceable. Rejected: treating both contexts as one implementation layer, retaining `eschema.snapshot()` through hidden registration or dependency injection, exposing introspection as public API, copying database-specific client/service/orchestrator names into ESchema, and keeping inheritance or a configurable universal builder. The wildcard `std-toolkit/eschema/*` export is removed so consumers cannot bypass the public boundary.
