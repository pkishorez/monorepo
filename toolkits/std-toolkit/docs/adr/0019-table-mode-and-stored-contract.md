# Every physical table has a mode, and setup checks a contract stored with the data

Every physical table is declared `persistent` or `disposable`, and adapter setup compares the table's contract with the **Stored contract** kept beside the data before it changes anything. This supersedes ADR 0012's "nothing is stored inside the table" and "setup never checks a snapshot", and ADR 0018's `acceptBreaking`.

ADR 0012 kept the only baseline in Alchemy state. That cannot protect a table Alchemy never sees. Each browser's IndexedDB and each Durable Object holds its own data at its own version: a device that last opened the app at v3 meets v5 directly, while the deploy guard only ever compared v3→v4 and v4→v5. A baseline in Alchemy state also outlives nothing it protects: lose the state and the guard starts fresh while the data remains. The baseline has to live exactly as long as the data does, so it lives with the data. The cold-start objection in ADR 0012 no longer applies, because setup runs only where no request pays for it: at deploy for D1, at process start for a SQLite file, on app open for IndexedDB, and on first access for a Durable Object. A hash beside the contract makes an unchanged contract one read with no comparison.

**The two modes.** A persistent table refuses a breaking or unverifiable change and never wipes; the fix is a code change or a new physical table name. A change that needs a backfill passes with a warning, since stored rows still read and the user decides when to backfill. A disposable table is wiped, whole, on any change its stored rows cannot take. Its schemas change freely, so it needs no `expectTableShippable`. A table may become persistent; a persistent table becoming disposable is refused, because otherwise one deploy could wipe it. The mode is declared per physical table, not on the StdTable, because one StdTable can be persistent in DynamoDB and disposable as a browser's copy.

**Per adapter.** SQLite (every driver, D1 and Durable Objects included) keeps the contract in a `_std_contract` table and IndexedDB in a `_std_contract` store in the same database. Only IndexedDB backfills, because its data is local and small: a persistent store always reindexes, and a disposable one chooses `reindex` or `wipe`. DynamoDB keeps no Stored contract: Alchemy creates its table, and a contract would need to be split across items to fit the 400 KB item limit. Its deploy guard is its only check, and it never replaces or wipes the table. DynamoDB adds a global secondary index in place but makes any other index change by replacing the table, and the guard and the table are separate Alchemy resources, so a deploy that stops between them could replace a table the guard already accepted. So in either mode a DynamoDB table refuses a breaking change and every index change except adding a global secondary index, including a new order of its local secondary indexes, which the snapshot does not record but DynamoDB replaces on. A new physical name under the same resource is refused as well, since Alchemy makes it by replacing the table; the way past is a new `DynamoDB.table` resource, with its own id and table name. A disposable DynamoDB table is therefore never wiped for you. Memory takes no mode, since nothing outlives it.

**The deploy guard stays, as an earlier check.** The Alchemy resource, renamed from snapshot guard to deploy guard, keeps the **Deployed contract** and refuses a persistent table's breaking change before it reaches any device or object. D1 and DynamoDB tables include it; `DeployGuard.table(table)` declares one for a table Alchemy does not create, named after the StdTable, with no mode, since declaring it says the table is persistent.

**Setups that race.** Two tabs, two Durable Object activations, or two releases can set up the same table at once. Every write of the Stored contract holds only while the contract is still the one setup read, and a wipe is made in the same atomic step as that write (one SQLite batch, one IndexedDB transaction), so a setup deciding on a stale read never wipes or overwrites; it starts over from the contract the other recorded. The contract is keyed case-insensitively in SQLite, since SQLite table names are. In the browser, an app runs one version across all its tabs, which its service worker enforces, so a tab running older code is out of scope; the guards above are there for two setups of the same version. A deploy guard compares the physical table it was given with the one it last checked when it runs, not when Alchemy plans, since a new database's id is only known then; the guard keeps one contract per physical table, so a new table name starts fresh while a table moved away from, even by a deploy that never finished, keeps its own.

## Considered Options

- **The baseline only in Alchemy state** (ADR 0012): rejected for the device and Durable Object cases above.
- **A dummy D1 database recording a Durable Object's schema**: rejected. Only each object knows the state of its own data, and the guard-only resource already gives the deploy-time check.
- **`acceptBreaking`**: removed. An agent could write the entry, and a persistent table that takes a breaking change is what the whole mechanism exists to prevent.
- **A third, semi-disposable mode**: rejected as a distinction nothing acts on.

## Consequences

`@kestack/std-toolkit/db/sqlite` and `/db/idb` now import snapshot, so removing snapshot no longer leaves the runtime compiling, and a Worker bundle that sets up a SQLite table carries the snapshot code. Existing tables are adopted: a table with no Stored contract records its first one and keeps its rows. Deploy guards are a new resource type with new ids, so each records a fresh Deployed contract on its first deploy; Alchemy deletes the retired snapshot guards, whose type stays registered for that alone. The apps move to new D1 databases at the same time, so no table keeps rows from before its first contract. A deleted deploy guard removes only the early check, since setup still refuses against the Stored contract.
