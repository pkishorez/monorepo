# The snapshot lives in the table, as three internal entities

Every StdTable keeps its own snapshot as ordinary entities in its own physical table, and every check reads that and nothing else. This supersedes ADR 0012, ADR 0019's storage (the `_std_contract` table and store, the Deployed contract in Alchemy state, and DynamoDB keeping no stored contract) and its `DeployGuard.table`. ADR 0019's two table modes stay as they were.

## Decision

**Three internal entities.** `StdTable.make(...).build()` registers them in every table, before any entity of the app's, so they are in `registeredEntities` and in the table snapshot like any other entity, and they guard themselves. An entity name starting with `__` is reserved for them. Together their items are the table's **Stored snapshot**.

- `__snapshot`, a single entity, one item per physical table: `logicalName`, `mode` (`persistent` or `disposable`), `primary` (`{ pk, sk }`), `localSecondaryIndexes` and `globalSecondaryIndexes`, each `{ name, pk, sk }`, and, from its v2, `hash`, the snapshot's hash or null (below). `hash` came as a new version, not an edit of v1, because tables had already stored v1 items: a v1 item reads as `hash: null`, so its table is checked in full once. The local secondary indexes are kept in the order the table declares them, which the table snapshot does not keep (it sorts them by name), because DynamoDB replaces a table whose order changes.
- `__snapshot_entity`, keyed by `name`, one item per entity: `name`, `kind` (`keyed` or `single`), `schema` (the identity of the ESchema it stores), `idField` (null for a single entity), `primary` (`{ pk: string[], sk: string[] }`) and `accessPatterns`, exactly as a table snapshot records an entity.
- `__snapshot_version`, keyed by `id` (`<schema>@<version>`), one item per version of every ESchema the table reaches, nested ones included: `id`, `schema`, `version`, `position` (its place in the schema's version list, from 0), `kind` (`struct`, `value` or `entity`), `idField` and `shape`. The shape is held opaque, as a snapshot type, and joining the items reads it through the snapshot type language.

`__snapshot_entity` and `__snapshot_version` derive their partition key from nothing, so each is one partition that one query reads whole. `kind` and `idField` belong to a schema, not a version; every version item carries them, and joining the items refuses ones that disagree.

The fields are the entities' own, not the snapshot document's, so a change to the document never silently changes what a table stores. A version item is close to write-once. A new version is a new item. An old version's item changes only when one of its checks is loosened, which ADR 0018 counts as safe; any other edit to it is breaking, so it is refused, or wiped with a disposable table.

The three are entities like any other: the app may read them, through read-only surfaces on every StdTable (`table.storedSnapshot`) or joined (`storedTableSnapshot(table)` in `@kestack/std-toolkit/db`), and table-wide reads (`scan`, sync, replicas, change notices) skip them. Only setup writes them. `dangerouslyRemoveAllItems` on the table leaves them, since they describe the physical table, not its rows.

**The hash.** `__snapshot.hash` makes an unchanged table one read. It is the SHA-256, in hex, of the canonical JSON (keys sorted) of every value the three entities' items hold for the code's snapshot, the declared order of the local secondary indexes included, and the mode left out, since `__snapshot` holds the mode beside it. It is everything the full check compares, so equal hashes mean the stored items are the code's. The hash is computed through WebCrypto (`crypto.subtle`), which browsers, Workers, Node and Bun all have, once per table and process: the snapshot is captured once per table and count of registered entities, since an entity may register after the table is built. It is cryptographic and not a fast hash because the fast path trusts it alone: a collision would skip a check and let a breaking change through, and SHA-256 costs a few hundredths of a millisecond once per process.

The invariant: **`hash` is non-null only when every snapshot item in the table matches it.** The last `__snapshot` write of a successful setup records the code's hash. Every earlier `__snapshot` write, the one that comes first when other items change, writes `hash: null`, so a setup stopped midway leaves no hash and the next setup checks in full, whatever code it runs. A full check that finds nothing changed but a missing or stale hash records the hash, in one write under the usual `_u` condition.

**One check, for every database.** The check, in `src/db/table-snapshot/`, is written once, over the **StdTable contract** every adapter already provides:

0. Read `__snapshot` alone. When its hash and mode are the code's, the table is unchanged: nothing else is read and nothing is compared. Otherwise:
1. Read the three entities' items. With none, a table with no rows records the code's snapshot as its first one. A table that has rows but no snapshot keeps them under the code's snapshot when it is persistent, and is wiped when it is disposable.
2. Otherwise join every `__snapshot_entity` and `__snapshot_version` item, under `__snapshot`, into the stored table snapshot, and diff it against the code's (`TableSnapshot.diff`). Entity or version items with no `__snapshot`, which a first write stopped before its last item leaves, are still the baseline: they are joined under the code's topology, and since their mode is unknown, their data is taken as persistent. Nothing scans for rows then.
3. A persistent table refuses a breaking or unverifiable change, a stored snapshot it cannot read, and a switch to disposable, and changes nothing. A disposable table is wiped, whole, on a change its rows cannot take and on a stored snapshot it cannot read. A change that needs a backfill passes on a persistent table with a warning; on a disposable one it wipes, unless the adapter reindexes.
4. Write only the items that changed, each under its own condition (`not-exists` for a new item, `updated` against the `_u` read for a changed one), in this order: when one is stored and any other item changes, `__snapshot` with the indexes the code adds, no hash, and nothing else changed; the versions, each schema after the schemas its versions name and each schema's versions by position; the entities; tombstones for what the code no longer has; and `__snapshot` as the code has it, last, with its mode, the indexes it removes and its hash. A condition that fails means another setup wrote first: start over from step 1, at most three times.

Planning is apart from writing (`planTableSnapshot` and `checkTableSnapshot`), so a target can check without writing; `readForCheck` reads what either needs, `__snapshot` alone on an unchanged table. Each adapter keeps its own topology steps on the fast path, which skips only the snapshot reads: IndexedDB still reconciles its store's indexes, SQLite its table's, and the DynamoDB check still compares the live table and its previous props. No step needs a transaction. A setup stopped between two writes leaves every item either at its old value or its new one, and the order makes every such prefix join into a stored snapshot the next setup compares against, whether it runs the same code or the code before: no entity names an index `__snapshot` lacks, no version names a schema with no version stored, no schema's versions have a gap, and the mode changes only with the last write. The final `__snapshot` is the commit point for the mode, for removed indexes and for the hash. Tombstones follow only a wipe, which leaves no rows a stopped write could strand; a prefix that does not join is wiped again. A disposable table is wiped before its snapshot is written, never after, and an adapter that can wipes only while `__snapshot` is still the one it read.

**Where it runs.** The check runs where no request pays for it:

| Database       | When                    | How                                                                                                                  |
| -------------- | ----------------------- | -------------------------------------------------------------------------------------------------------------------- |
| D1             | at deploy               | the `D1.table` Alchemy resource runs SQLite setup against the database                                               |
| DynamoDB       | at deploy               | a check resource before Alchemy's table, and a record resource after it                                              |
| SQLite file    | at process start        | `SQLite.setup`                                                                                                       |
| Durable Object | in the constructor      | `SQLite.setup`, inside `blockConcurrencyWhile`                                                                       |
| IndexedDB      | when the database opens | IDB setup, after creating a missing store and before changing an existing store's indexes, or `IDB.setup` beforehand |
| Memory         | never                   | nothing outlives it, so it takes no mode                                                                             |

**DynamoDB at deploy.** `DynamoDB.table` is three resources, each ordered after the one before by its output:

1. `${id}SnapshotCheck` (`StdToolkit.DynamoDB.SnapshotCheck`) changes nothing. Against its own previous props it refuses a new physical name and any change Alchemy makes by replacing the table: a new primary key, any index change but adding a global secondary index, and a new order of the local secondary indexes. If the table exists, it refuses the same replacements against the table's own keys, from `DescribeTable`, then reads the Stored snapshot from it and plans against it, refusing a breaking change, a switch to disposable, and the same replacements again. A table that does not exist yet passes.
2. Alchemy's native `AWS.DynamoDB.Table`, whose `tableName` comes from the check's output, so it waits for the check.
3. `${id}SnapshotRecord` (`StdToolkit.DynamoDB.SnapshotRecord`) runs the check again against the table as it is now and writes the items that changed, in the order above. Its wipe refuses, so a DynamoDB table is never wiped, in either mode.

The check compares against the live table's keys because an existing table can have neither a Stored snapshot nor previous props: on its first deploy under this release, or after Alchemy's state is lost. `DescribeTable` lists local secondary indexes in an order of its own, not the declared one, so only the other two can refuse a new order of them. The check compares against both the Stored snapshot and its own previous props because a deploy can stop after Alchemy updated the table and before the record ran. The table then has the new layout and the old snapshot; a revert compared only with the snapshot would pass and have Alchemy replace the table. Its cost: if the table update itself failed, a revert is refused until the previous deploy is redeployed. DynamoDB is never wiped, so a table with rows but no snapshot keeps them in either mode, and nothing scans for rows. Since the check and the record each plan, the plan's logs print twice.

Both providers read `AWSEnvironment` from the stack, so `DynamoDB.table` needs `AWS.providers()` under std-toolkit's `providers()`; without it the deploy fails saying so. `@alchemy.run/aws` is imported lazily, only when a DynamoDB table deploys: it takes seconds to load, and a stack with no AWS resource never needs it. `DynamoDB.describeTable(config)` in `@kestack/std-toolkit/db/dynamodb`, the live table's keys or `undefined` when it does not exist, is an adapter-native operation the check uses. The check's reads are strongly consistent, `getItem` and the contract's `queryItems` with `consistent` alike, so a deploy right after another reads every item it wrote. Nothing else is kept in Alchemy state.

Under `alchemy dev`, Alchemy's native table stays on real AWS while the context std-toolkit's providers read points at the emulator, so the check and the record read and write a different table than the one Alchemy changes. No app uses `DynamoDB.table` yet; this is a known gap.

**Migrations.** `src/migrations/` holds the code that moves data from a layout std-toolkit no longer writes to the one it does. Each migration is a folder named after the release it ships in. It imports nothing that may change: whatever it needs of the old layout, it copies. The rest of the toolkit calls it through fixed entry points that stay, doing nothing, when no migration is registered: `Migrations.sqlite` and `Migrations.idb` in `src/migrations/index.ts`, and `AlchemyMigrations` in `src/migrations/alchemy`, kept apart so a browser or Worker bundle never loads Alchemy. Deleting a migration is deleting its folder and its lines in the entry points. A change to the internal entities' own format is not a migration: it is a new version of their ESchema, like any entity's.

The first, `2026-11-stored-contract`, has three parts:

- SQLite: when a table has no `__snapshot` item and its `_std_contract` row reads, it records that snapshot and mode as the table's, then deletes the row, and drops `_std_contract` once it is empty. A row that does not read is deleted with a warning, and setup goes on as for a table with no snapshot. It runs before the check, so the check compares against what was moved and a breaking change is still refused. `_std_contract` stays a reserved table name.
- IndexedDB: the leftover `_std_contract` store is deleted, in the same version change that creates the table's store. Nothing in it is moved: every IndexedDB table in this repo is disposable, so a store with rows and no snapshot is wiped once, and a persistent one keeps its rows under the code's snapshot. `_std_contract` stays a reserved store name.
- Alchemy: the retired `StdToolkit.DeployGuard` and `StdToolkit.SnapshotGuard` resource types stay registered, so Alchemy can delete them from a stage's state. Deleting one touches nothing.

## Considered options

- **The baseline in Alchemy state** (ADR 0012) and **a `_std_contract` table beside the data** (ADR 0019): rejected. The first is lost with the state, and neither is one model for every database: DynamoDB kept no stored contract at all.
- **One item per table, or per entity**: rejected for DynamoDB's 400 KB item limit. One item per version keeps every item small however many versions an entity reaches.
- **A transaction around the whole write**: rejected as unneeded, for the reason above; per-item conditions stop two setups racing.
- **No hash, joining and diffing every item on every setup**: the first form of this decision. It cost 3.0 ms per IndexedDB reopen under fake-indexeddb, against 0.2 ms for the earlier single-hash design; the hash brings it to 0.1 ms.
- **A fast, non-cryptographic hash**: rejected. The fast path trusts the hash alone, so a collision would silently skip a check, and SHA-256 runs once per table per process.
- **A hash that also stands guard against racing setups**: not attempted. Without a transaction, a setup of other code racing this one can still land an item after this one records its hash; the hash then hides that item until the code changes, where before the next full check would see it. Setups of the same code race safely, as before.
- **An Alchemy check for Durable Objects and IndexedDB** (`DeployGuard.table`): removed. Alchemy cannot see each object's or device's data; the committed snapshot file, checked by `expectTableShippable` in CI, is the earlier check.

## Consequences

Every committed table snapshot file gains the three internal entities and their schemas. The check runs at deploy for D1 and DynamoDB, so a breaking change fails there before anything ships; for Durable Objects and IndexedDB it runs after the code is live, so a breaking change that passed CI makes those objects or devices refuse to open, with their data kept. Existing SQLite files, D1 tables and Durable Objects are migrated on their next setup; a table that never runs setup before the migration is deleted takes the code as its baseline and keeps its rows. Existing IndexedDB disposable stores are wiped once. An existing DynamoDB table has no snapshot, so its first deploy under this release records the code's as its first, its entities checked only by the committed file and its keys against the live table. A stack that deploys `DynamoDB.table` must provide `AWS.providers()`.
