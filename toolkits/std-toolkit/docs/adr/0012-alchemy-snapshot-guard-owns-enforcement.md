# An Alchemy snapshot guard owns enforcement, at deploy only

Table-level enforcement moves out of the table and out of every adapter. `std-toolkit/alchemy` is a new top-level module and the only place snapshot meets a deploy. It has one folder per deploy target, `dynamodb` and `d1`, plus a shared `snapshot-guard`. On each deploy, the toolkit captures the table snapshot, diffs it against the accepted one, and fails with `SnapshotIncompatible` when the change is `breaking` or `unverifiable`. A `requires-backfill` change is accepted with a warning. The physical identity is a DynamoDB table name or a D1 database id and table name. A new target starts a fresh baseline. `DynamoDB.table` puts a guard resource before Alchemy's native table resource. `D1.table` registers one custom resource whose provider checks the snapshot before it calls `SQLite.setup`; the accepted snapshot is saved only when setup succeeds. Neither target changes a physical table after the snapshot check refuses it. This supersedes ADR 0010: the DynamoDB table resource moves from `std-toolkit/db/dynamodb/alchemy` into `std-toolkit/alchemy`.

Adapters go back to `make` returning the layer. SQLite and IndexedDB keep a standalone `setup` because nothing else creates their tables; DynamoDB keeps `createTable` and `deleteTable` for DynamoDB Local. None of them reads a snapshot. `table.snapshot()` is gone: `TableSnapshot.capture(table)` reads a table structurally, so db and snapshot no longer import each other, and removing snapshot leaves the runtime compiling. New deployments no longer write the old reserved snapshot item. Table scans still filter that item while existing physical tables can contain it; adapter setup does not manage it. `BaselineMissing`, version floors, and owed backfills are removed.

The earlier design ran enforcement inside every adapter's `setup` against a baseline stored inside the table. In a serverless runtime a layer is rebuilt often, and a check that reads and diffs a snapshot does not belong on that path. The baseline item also grew with every version of every schema and shared the item size limit with real rows. Alchemy's resource lifecycle is already the enforcement loop: it hands the provider the output it accepted last time, and a failed update is a failed deploy, which is where a refusal belongs.

Rejected: keeping the baseline in the table, for the size and cold-start reasons above; a sidecar table or blob store, because Alchemy state already exists for every deployed stack; and fusing setup and enforcement into one unskippable adapter call, because with the guard in the deploy there is nothing left to fuse. The trade-off is that the guard is only as durable as the Alchemy state store, and a table deployed without `std-toolkit/alchemy` has no guard.
