# An Alchemy snapshot guard owns enforcement, at deploy only

Table-level enforcement moves out of the table and out of every adapter. `std-toolkit/alchemy` is a new top-level module and the only place snapshot meets a deploy. It has one folder per deploy target, `dynamodb` and `d1`, and the shared `snapshot-guard` they both use. The guard is a custom Alchemy resource that keeps the last accepted table snapshot in Alchemy state. On each deploy it captures the table snapshot, diffs it against the accepted one, and fails the deploy with `SnapshotIncompatible` when the change is `breaking` or `unverifiable`. A `requires-backfill` change is accepted with a warning. The guard carries the physical identity it protects, a table name or database id, so a new target replaces the resource and starts a fresh baseline. `DynamoDB.table` creates the table resource with every index, then guards it. `D1.table` guards first, then runs an action that calls `SQLite.setup`, so the table is never reconciled to a shape the guard refused. This supersedes ADR 0010: the DynamoDB table resource moves from `std-toolkit/db/dynamodb/alchemy` into `std-toolkit/alchemy`.

Adapters go back to `make` returning the layer. SQLite and IndexedDB keep a standalone `setup` because nothing else creates their tables; DynamoDB keeps `createTable` and `deleteTable` for DynamoDB Local. None of them reads a snapshot. `table.snapshot()` is gone: `TableSnapshot.capture(table)` reads a table structurally, so db and snapshot no longer import each other, and removing snapshot leaves the runtime compiling. The reserved baseline item, its scan filter, `BaselineMissing`, version floors, and owed backfills are removed. SQLite setup deletes the reserved item that earlier releases wrote, so it never appears in a scan.

The earlier design ran enforcement inside every adapter's `setup` against a baseline stored inside the table. In a serverless runtime a layer is rebuilt often, and a check that reads and diffs a snapshot does not belong on that path. The baseline item also grew with every version of every schema and shared the item size limit with real rows. Alchemy's resource lifecycle is already the enforcement loop: it hands the provider the output it accepted last time, and a failed update is a failed deploy, which is where a refusal belongs.

Rejected: keeping the baseline in the table, for the size and cold-start reasons above; a sidecar table or blob store, because Alchemy state already exists for every deployed stack; and fusing setup and enforcement into one unskippable adapter call, because with the guard in the deploy there is nothing left to fuse. The trade-off is that the guard is only as durable as the Alchemy state store, and a table deployed without `std-toolkit/alchemy` has no guard.
