# The Auth Worker handler serves its own pages, prebuilt inside the toolkit

The Authorization Server Role needs login, consent, and device approval pages built on kui-toolkit and React, and kui ships raw source that only a Vite and Tailwind build can compile. The toolkit therefore contains a TanStack Start app that renders those pages, builds it with its own Vite step, and embeds the client assets as strings; the `auth-toolkit/worker` door resolves at runtime to that bundle, so `createAuthWorker(...).handler` serves `/api/auth/*`, the pages, their assets, and Start's server-function calls from one function. A consumer keeps bootstrapping the Worker itself: an `alchemy.run.ts` with a plain `Cloudflare.Worker` whose `main` calls the handler. We rejected scaffolding the app into each consumer, because it made the page components public doors and every deployment its own copy of the app; a headless Worker plus an Assets binding, because it needed config injection into static HTML and a binding the consumer must wire; and shipping the whole deployment as one alchemy resource, because it took the Worker's composition away from the consumer and forced every setting through env. Embedding costs about one megabyte of script, which Cloudflare's limits absorb.
