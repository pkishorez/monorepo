# MCP clients register themselves

An Auth Worker that serves MCP Servers opens Client Registration to `dynamic+cimd`: unauthenticated Dynamic Client Registration (RFC 7591) and Client ID Metadata Documents, side by side. Every MCP client today registers dynamically; the MCP 2026-07-28 revision makes metadata documents the default and deprecates dynamic registration with a twelve-month window, and Claude Code already prefers them. Running both lets clients migrate without the Auth Worker changing again, and a self-registered Client Application still cannot act until a User logs in and consents, so openness here costs consent-page noise, not access.

Two details are deliberate. First, a registration that omits `application_type` and redirects only to plaintext loopback URLs is stored as a native client, the RFC 8252 reading of that shape, because the provider's `web` default would reject exactly how the MCP Inspector registers; web clients are still held to HTTPS redirects. Second, better-auth's own CIMD transport uses `node:https` with DNS pinning, which Cloudflare Workers cannot run. The toolkit's transport is plain `fetch` with `redirect: 'manual'`, because workerd rejects the plugin's `redirect: 'error'` and the plugin refuses every non-200 answer anyway. The DNS checks the Node transport performs guard against a metadata URL that resolves to a private address; a Worker's `fetch` cannot reach private or loopback addresses, and the plugin rejects literal private hostnames before calling the transport, so those checks are not repeated here.
