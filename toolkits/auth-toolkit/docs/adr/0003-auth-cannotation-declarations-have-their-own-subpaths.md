# Auth Cannotation Declarations have their own subpaths

The Auth Cannotation for each Sibling is declared with rpc-toolkit's `Cannotation.make`, and rpc-toolkit's ADR 0001 requires a Declaration to be importable from contract code shared with the browser. auth-toolkit therefore exposes `auth-toolkit/rpc` and `auth-toolkit/http-api` as Declaration doors, each exporting the single `Authz` object and keeps `auth-toolkit/rpc/server` and `auth-toolkit/http-api/server` for the Server Implementation (`authzLayer`, `resolverLive`, and for RPC `authzCookies`), with no symbol on both doors and no standalone type exports. We rejected one door per Sibling because it drags the Auth Worker verifier and better-auth runtime into the contract bundle; better-auth's `User` and `Session` remain as type-only imports in the Declaration since consumers already depend on better-auth for the Auth Worker. Each Declaration is an interior file of its Sibling's server module (`src/server/rpc/authz.ts`, `src/server/http-api/authz.ts`) and the contract subpath points straight at that file, so one module serves two subpaths: the Declaration exists for the sake of the Server Implementation next to it, and bundle safety is a property of what a subpath imports, not of where its file sits. `Authz` carries `guard`, `policy`, `CurrentAuth`, `Resolver` (the tag tests replace; its production layer is `resolverLive`), and the three errors (`Unauthenticated`, `Forbidden`, `VerificationUnavailable`) so a contract needs one import and one shared `resolverLive` can serve both Siblings; the raw Cannotation stays in an interior `cannotation.ts` so `get`, `layer`, `value`, and `middleware` are not public; the Cannotation's `with` is renamed `guard` because that is the auth-specific verb, and the rpc-toolkit shape stays untouched.
